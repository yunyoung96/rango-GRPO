<0. 가정>
일단 gbdt를 잘 만들었다고 가정해줘. 
아니면 다른 rrf 라던가

참고로 assert를 만드는 로직은 다음과 같아.
만약 gold tactic에서 gold lemma는 L이었는데, 
retrieval이 되지 않았어. 그래서 똑같은 signature을 가진 L'을 만들어서, 
그 다음에 바로 L' 을 증명해
예는 쉬운게 이미 L이 있으니까 L' goal을 대상으로 retrieval 되면 L이 높은 순위로 
와야 정상일거 아니야 (=> 만약 아니면 gdbt를 다시 설계해야겠지? 이게 된다는게 되게 높은 추측인데)
이렇게 하면 우리는 L'을 가설에 가지고 있으니까 
원래 L을 사용하던 gold tactic을 L'이라는 검증된 가설 lemma로 문제를 풀게 해줘. 그러면
retrieval 애 검색이 안 되던 문제는 어느 정도 풀리는 거겠지

그런데 
retrieval 검색 목록에 gold tactic이 사용하는 gold lemma인 L이 없음
-> 그래서 같은 signature를 가지는 L'을 일단 assert로 생성함.
-> 생성한 L'도 정답인 L을 retrieval 하지 못함
-> 이렇게 해서 남은 애들은 어쩔 수 없어. 비율이 적다면 (5%이하면)
Hallucination 감수하고 그냥 gold tactic 을 사용해.

참고로 주의해야할 사항은 gold tactic이 lemmas를 여러개 들고 있어서
assert를 여러개 들고 있어야 할 수 도 있어.
이걸 감안해줘

<1. 실험>
내가 원하는 실험은 다음과 같아. 이 실험은 아마도 
방법론이 업데이트 될때마다 해줘야 할거야. 

이 체크는 train, val, test 모든 set에서 다 진행해줘. 데이터 숫자도 넉넉히
apply have move rewrite 같은 lemma가 등장할 수 있는 tactic 순간에 대해서 아래 체크를 진행해

A. gold premise가 retrieval된 애들 중에 있는 비율 (top 1, 20, 50) 전부 다 체크해주고
B. gold premsie가 있던 없던 같에 assert를 성공적으로 만들었는지, 그리고 assert로 갈아 끼워도
뒤에 있던 suffix proof를 그대로 적용해도 아무런 문제 없이 동작하는지
C. 그리고 gold premsie L을 본떠서 만든 L'에 대해서 assert를 하고 직후에 L'를 gold lemma로 
만들었을때, L을 본따서 만든게 L' 이니까 
상식적으로 L이 retrieval 했을때 높은 순위에 올라와야 할거 같은데
잘 retrieval 되었는지 검사해줘. (top 1, 20, 50) 모두 봐줘.
=> gold premise L을 못찾은 애들에 대해서 L'을 만들고 L이 잘 retrieval 검사 되는 비율을 봐달라는거지
D. 기타 생각지도 못한 문제를 마주치면 보고해줘. 
E. 이 외에 다양한 동적 디버깅

목표. A가 높게 나오는게 제일 좋고, C까지 높아서,
A의 recall + C의 assert 이후 recall이 90 ~ 95퍼는 나와야 쓸만할거 같아. 

=> 만약 실험 결과가 좋지 않아 (A, C의 recall 이 너무 낮아)
그러면 다시 0번으로 돌아가서 gbdt를 다시 학습하던가 설계를 다시 해줘

<2. 검증>
정규화를 하면서 바뀌는 이름이 있을 수 있기 때문에 이름이 겹치지 않게 빡세게 해줘.
아니면 이름 규칙을 하나로 통합한 다음에 (기존 흩어져있었으면 정규화를 하나의 함수로 합치는거지)
각각의 동작은 함수 호출시에 플래그를 넣어서
이렇게 하고, 각 context마다 이름 set을 만들어서 정규화로 이름을 붙일때마다
이 set에 있는지 검사하고 이미 있으면 다음 index로 건너뛰고 이래야 할거 같은데

<5-0. 왜 다시 재나>

기존 A/B/C 는 전부 **검색 순위 top-k** 기준으로 쟀다. 그런데 실제 기준은
"premise 토큰 예산 안에 살아남아 **프롬프트에 들어가는가**" 다.

  검색이 넘긴 premise    100개 (num_premises)
  프롬프트에 들어간 것    10~20개   ← 예산 896 토큰
  ★ 70~80% 가 잘린다

premise 길이 편차가 극심하다 — 최소 16 · p25 43 · 중앙 147 · 최대 928 토큰.
긴 것 하나(175토큰)가 짧은 것(20토큰) 여러 개를 밀어낸다.

예비 측정에서 A 가 절반으로 떨어졌다.

  A · structural · ALL      검색 순위 기준 45.4%  →  프롬프트 기준 26.0%
  C · structural · ALL      검색 순위 기준 90.4%  →  프롬프트 기준 97.1%

(C 는 오히려 오른다. cut 을 세우면 그 명제가 정확히 goal 이라 최상위로 온다.)


<5-1. 검색은 3단으로 겹쳐 있다>

  ① SparseClient.get_premise_scores
       tfidf → structural 재랭킹 → 상위 100개
       (cached_premise_loc 이 없으므로 실시간 계산)
  ② rerank_premises  (collate_input, RERANK_PREMISES=1)
       점수 = (원순위 prior: n-i) + 30×타입매칭
       ★ ①의 순위를 prior 로만 쓰고 다시 흔든다
  ③ allocate_and_fmt
       예산까지 담기 → 중앙 10~20개

지금까지 보고한 gold 포함률은 **①②③을 다 통과한 값**이다.

★ 확인 필요: ①이 이미 구조 신호를 쓰므로 ②와 정보가 겹칠 수 있다.
  RERANK_PREMISES on/off 비교가 필요하다(계층 랭커에서 "신호를 겹쳐 쓰면
  오히려 나빠진다"를 이미 겪었다).

<9. U1 재측정 — ★ 하위스텝은 U1 을 고치지 못했다 (아침 보고를 정정한다)>

  <9-1. 세 번의 오측정>

  같은 검사를 새 계획 파일로 다시 돌리니 U1 이 0 으로 나왔다.

    scan_prompts 300건   U1 0 / cut 14건
    scan_prompts 1200건  U1 0 / cut 48건

  **셋 다 틀렸다.** 검사기가 `if "H_asrt" in target` 으로 cut 을 판정하는데,
  `close` 하위스텝의 정답은 `exact L.` 뿐이라 H_asrt 가 없다. 그래서 close 를
  전부 "cut 아님" 으로 버렸다 — **U1 이 사는 자리를 통째로 버리고 "U1 없음" 을
  얻은 것이다.**

  1차 수정으로 `^\{\s*e?exact\b` 를 추가했더니 **또 0** 이었다. 실제 분해를 찍어 보니

      assert | 'assert (forall n m, n + m = Nat.iter (N.to_nat n) N.succ m) as H_asrt0.'
      close  | 'exact Nadd_alt.'          ← **중괄호가 없다**
      final  | 'induction d; …'

  `_SUB_ASSERT` 의 4번 그룹이 중괄호 **안쪽**을 잡으므로 close 는 `exact L.` 이다.

  → 텍스트로 추측하는 것을 그만두고 **학습이 쓰는 함수**(`LmDataset._substep_plan`)
    에 물어 `subs[pick][1]` 을 그대로 읽었다. cut 은 런타임에 "안 보이는 lemma" 만으로
    다시 조립되므로 계획 파일만으로는 pick 을 계산할 수 없다 — 데이터셋에 물어야 한다.

  ※ 교훈: **파이프라인이 만든 것의 종류를 검사기가 텍스트로 되짚지 마라.**
    같은 함수에 물으면 한 번에 맞고, 겸사겸사 그 함수가 도는지도 검증된다.

  <9-2. 진짜 값>

    cut 프롬프트 300건 (시도 552건)
      하위스텝 assert  106
      하위스텝 close    83     ← 앞선 검사기들이 전부 버리던 것
      하위스텝 final   110
      통짜 cut           1

      exact 대상          85
      ✓ 프롬프트에 있다    39
      U1 ★ 없다           46      **가시율 45.9%**

  원래 값이 12/23 = 52% 였다. **하위스텝은 U1 을 고치지 못했다.**

  <9-3. 왜 — 재검색은 정상이고, 후보 풀에 없다>

  U1 사례를 단계별로 추적했다.

    idx=1796002  close  'exact negb_involutive.'
      assert P    forall b : bool, negb (negb b) = b
      재검색 후   premises 81개 · goal = 'forall b : bool, negb (negb b) = b'   ← ✓ 정상
      L 이 검색 결과에 있나       **아니오**
    idx=658150   close  'exact pos_INR.'
      assert P    forall n:nat, 0 <= INR n
      재검색 후   premises **2개** · goal 정상
      L 이 검색 결과에 있나       **아니오**

  재검색(G1)은 정확히 작동한다 — goal 이 assert 명제 그대로 들어간다. 문제는 그 위다:

    src/premise_selection/premise_filter.py

      from_coq = os.path.join("lib", "coq", "theories") in premise.file_path
      if from_coq and (premise.sentence_type in self.coq_excludes):
          return False          ← stdlib 의 LEMMA/THEOREM 은 **풀에서 제외**

  `negb_involutive` · `pos_INR` · `map_length` · `CRplus_0_r` 는 전부 stdlib 다.
  즉 `exact L` 이 **검색으로 도달 불가능한** 이름을 요구한다.
  (이건 rango 원본의 필터 설계다. 우리가 넣은 것이 아니다.)

  <9-4. 고침 — 하위스텝 셋은 성격이 다르다>

    assert  `assert (P) as H.`   goal 로부터 **필요한 명제를 추론**한다 → 정당한 학습 신호
    final   `apply H_asrt0.`      자명 → 정당
    close   `exact L.`            **순수 이름 회상** → L 을 못 보면 환각 학습

  close 만 검색에 의존한다. 그래서 재검색 뒤에도 L 이 안 보이면 **같은 lemma 의
  assert 스텝(pick−1)으로 물러선다.** 그건 명제를 goal 에서 추론하는 문제라
  프롬프트만으로 풀 수 있다.

  ★ 설계 자체가 틀린 것은 아니다 — 39/85 는 재검색으로 실제로 찾았다.
    풀에 있는 lemma 에 대해서는 하위스텝이 의도대로 작동한다. 가드가 없었을 뿐이다.

  <9-5. 가드를 세 번 조였다 — 45.9% → 95.5%>

    가드                          exact 대상   안 보임   가시율
    (없음, 하위스텝만)                    85        46    45.9%
    ① `_fit_premises` 만                  2         1    ← **과잉 폴백**
    ② + proofs 전량                      54        23    57.4%
    ③ + proofs 를 collator 예산으로       22         1    **95.5%**

  ①이 과잉인 이유는 **`[PROOFS]`** 다. 유사 증명이 그 lemma 를 쓰는 줄을 담고 있으면
  모델은 이름을 읽을 수 있는데 premise 만 보면 못 센다 — 실제로 보이는 39건까지 버렸다.

  ②는 반대로 낙관했다. proofs 원본엔 있는데 `[PROOFS]` 섹션이 **예산에 밀려 0자**가
  되는 경우가 있다(실측: pos_INR · CRplus_0_r 는 proofs 원본 2~12개에 있었지만
  [PROOFS] 는 0자였다). collator 와 **같은 함수·같은 예산**(`allocate_and_fmt`,
  `proof_tokens`)을 써야 맞는다.

  ※ 교훈: "프롬프트에 보이는가" 를 판정하려면 **프롬프트를 만드는 것과 같은 예산 함수**를
    써야 한다. 원본 리스트를 세면 낙관하고, 한 섹션만 세면 비관한다.

  그리고 폴백 시 되돌릴 것이 둘 더 있었다.
    ① 예제 — 재검색은 `goal = P` 로 한 것이라 `assert` 스텝에는 안 맞는다.
       원래 goal 로 뽑힌 premise 를 봐야 다른 assert 스텝과 조건이 같다.
    ② 기준 상태 — `_substep_state` 는 **원래** proof_state 를 받아야 한다.
       바뀐 예제에서 읽으면 이미 한 번 가공된 상태가 들어간다.

  남은 1건(0.33%)은 하위스텝 분해가 실패해 **통짜 cut** 이 쓰인 경우다.
  통짜는 `assert (P) as H. { exact L. } apply H.` 를 한 스텝에 내야 하므로
  **구조상 `exact L` 이 항상 안 보인다** — 그게 하위스텝을 만든 이유다.
  (`cut_substep` 가드가 있어 하위스텝과 통짜가 겹쳐 적용되지는 않는다.)

  <9-6. 남는 한계 (해결하지 않았다)>

  stdlib lemma 를 쓰는 스텝은 이제 `assert (P) as H.` 까지만 학습한다. 추론 시
  모델이 그 assert 를 내면 **닫을 방법이 없다** — `exact <이름>` 을 지어내야 하는데
  그게 바로 우리가 피한 것이다.

  근본 해법 후보 셋:
    (a) stdlib 을 후보 풀에 넣는다 — rango 의 PremiseFilter 를 바꾸는 큰 변경이다.
        풀이 수만 개 커지므로 검색 비용과 A 지표를 다시 재야 한다.
    (b) close 를 `auto`/`lia`/`now auto with *` 같은 **자동화**로 바꾼다 —
        gold 증명을 바꾸는 것이므로 Coq 으로 검증해야 한다.
    (c) 그 스텝을 hopeless 로 강등한다 — 가장 안전하지만 학습량이 준다.
  지금은 (c) 에 가까운 상태(=close 를 안 쓴다)이고, (a)/(b) 는 다음 실험이다.

  건너뛰고 finally 는 파일만 복원한다 → coq-lsp 가 영원히 산다.
  250스텝에서 27개(≈11%)가 샜다.

    고침: cf = None 으로 선언하고 finally 에서 close 를 보장 (4곳 전부)

  ★ 그리고 그 15시간짜리 측정은 **폐기된 산출물**을 재고 있었다(옛 cuts_train.jsonl).
    측정값 자체는 남긴다 — 옛 런타임 경로의 실패 유형이 새 경로를 정당화한다:

      변환 성공률(시도분)  213/250 = 85.2%
      실패 유형 상위
        assert (= (not x) : type_scope (default interpretation))   ← Check 출력을 재파싱
        assert (string) as H_asrt0. { exact (beq_string_false_iff). } ← 타입 일부만 잡음
        assert (tm -> tm -> tm -> tm) ... { exact m_trans. }        ← 인자 타입을 잡음

    셋 다 **Coq 의 출력을 다시 파싱한 데서** 나온다. Coq 의 출력은 항상 다시
    파싱되지 않는다(notation·evar·암묵인자).

    새 계획 파일은 premise 풀의 **원문 명제**를 그대로 쓰므로 그 경로가 없다.
    같은 m_trans 를 새 계획에서 보면

      assert (forall t t' u, eval_many t t' -> eval_many t' u -> eval_many t u)
        as H_asrt0. { exact m_trans. }
      eapply H_asrt0.

    맞다. hunt_assert_errors 에 PLANS=<jsonl> 모드를 넣어, 같은 검증 기계
    (증명 지점 절단 · 원본 대조 · suffix 확인)로 **계획 파일의 cut 을 직접** 돌린다.


<12. tfidf 1단계 필터를 안 거치면 (jac_all)>

  요청받았으나 어젯밤 체인의 랭커 목록에서 빠져 실행되지 않았다. 구현은 되어 있었다.
  stage1=5,000 은 비용 때문에 둔 절단인데 실측 후보 풀이 중앙 7,378 · 최대 14,333 이라
  **68% 의 스텝에서 실제로 잘라내고 있다** — tfidf 가 조용히 상한을 정하고 있다.


<13. ★★ 학습이 재현되지 않고 있었다 — premise 풀 순서가 실행마다 달랐다>

  콜드/웜 스모크의 손실이 미묘하게 달랐다(4.956 vs 4.951 · grad_norm 0.8146 vs 0.8177).
  GPU 비결정성으로 보기엔 데이터가 같아야 하므로, 같은 인덱스의 **완성 프롬프트 해시**를
  별도 프로세스 두 개에서 찍어 비교했다.

    인덱스 7개 중 3개 불일치     len 2888 vs 2874 · 3356 vs 3412 · 4465 vs 4484
    PYTHONHASHSEED=0 고정 시     완전 일치

  → 원인은 **문자열 해시 랜덤화**다. 자리를 좁히니 [PREMISES] 44줄의 **내용과 순서**가
    달랐다(줄 수는 같다). 랭킹의 최종 정렬은 stable sorted 라 동점이면 입력 순서를
    따르는데, 그 입력 순서가 달랐다.

    src/data_management/dataset_file.py:642

      oof_premises: set[Sentence] = set()     ← 집합에 모으고
          oof_premises.add(premise)
      return list(oof_premises)               ← 집합 순회로 꺼낸다

      Sentence.__hash__ = hash((self.text, self.file_path, ...))   ← 문자열 해시

  파이썬의 문자열 해시는 PYTHONHASHSEED 로 **프로세스마다** 랜덤화된다. 실증:

      {'rem_plus','rem_plus_div','rem_rem','rem_diag','divides_rem_rem'} 를 list() 하면
        실행1  ['rem_plus_div','divides_rem_rem','rem_rem','rem_plus','rem_diag']
        실행2  ['rem_diag','rem_plus','rem_rem','divides_rem_rem','rem_plus_div']
        실행3  ['rem_plus','rem_rem','divides_rem_rem','rem_diag','rem_plus_div']

  <13-1. 무엇이 문제인가>

    · 학습이 **재현되지 않는다.** 같은 seed·같은 conf 로 돌려도 다른 프롬프트를 본다.
    · dataloader 워커가 spawn 방식이면 **한 번의 학습 안에서도** 워커마다 다르다.
    · 캐시에 무엇이 들어갔는지 알 수 없다 — 페이지를 처음 만든 프로세스의 seed 에
      우연히 고정된다.
    · 실험 비교가 오염된다. A/B 의 차이 중 일부가 순서 잡음이다.

  <13-2. 고침>

    집합은 **중복 판정에만** 쓰고 순서는 원본(file_context.avail_premises)을 따른다.
    __get_oof_avail_premises · __get_in_file_avail_premises 둘 다.

      seen: set[Sentence] = set()
      out: list[Sentence] = []
      for premise in self.file_context.avail_premises:
          ...
          if premise not in seen:
              seen.add(premise); out.append(premise)
      return out

    정렬(sorted)이 아니라 원본 순서를 쓴 이유 — 원본은 파일 내 선언 순서라 의미가 있고,
    정렬은 임의의 새 순서를 도입해 기존 실험과의 비교를 끊는다.

    확인: 임시 캐시를 써서(캐시 우회) 두 프로세스가 **바이트 단위로 일치**.

  <13-2b. 지금까지의 실험 결과는 살아 있는가 — 그렇다>

    랭커 비교(exp_abcd)는 **한 프로세스 안에서** 모든 랭커에게 같은 후보 풀을 주고
    같은 예제를 재므로, 순서 잡음이 **모든 랭커에 똑같이** 걸린다. 그래서 쌍 비교
    (McNemar)와 랭커 간 대소는 그대로 유효하다. 절대 수치에는 순서 잡음이 섞여
    있으므로, 다른 날 다른 프로세스에서 잰 값과 소수점 아래를 비교하면 안 된다.

    반대로 **학습 결과**를 두 번 비교하는 것은 지금까지 위험했다. 이제 결정적이다.

  <13-3. 캐시 무효화>

    프롬프트가 바뀌었으므로 기존 3.1GB 캐시는 무효다. 그런데 CACHE_STAMP 는 환경변수만
    찍고 있어서 **코드 변경은 안 걸린다** — 옛 페이지와 새 페이지가 조용히 섞인다.
    스탬프에 데이터 경로 버전을 넣었다.

      _DATA_PATH_VERSION = "v2-premise-order-deterministic"

    손으로 올린다. 소스 해시·mtime 으로 자동화하면 주석만 고쳐도 3GB 를 버린다.


<14. `[TfCLG]\d+` 오탐 — 다섯 번째>

  1,200건 스캔에서 N1 이 2건 떴다.

    idx=1912239  f1 · f2  ←  set V := Zo B (fun b => Vf f1 (J y b) = Vf f2 (J y b)).

  [STATE] 를 보면

    A, B: Set
    T: fterm2
    f1, f2: Set        ← **원본 파일의 지역 변수**다 (gaia 계열)
    f1a: surjection f1

  우리 정규화 이름이 아니다. 검사기가 막는 바람에 학습이 멈춘다.

  이 패턴의 오탐 이력:
    ① hopeless 정규화        ② cut 에 이름 누출 1,607건
    ③ 스캔 N1/N4             ④ preflight 의 destruct IN as [f1 ...]
    ⑤ [STATE] 의 가설 이름    ← 이번

  이제 지역 이름의 출처를 셋 다 본다: 이 tactic 이 도입하는 이름(introduced_names) ·
  [STATE] 의 가설 이름 · 프롬프트 안의 선언. 근본적으로 `[TfCLG]\d+` 는
  **정규화 이름의 충분조건이 아니다** — 실제 Coq 코드에 흔한 이름꼴이다.


<15. 도구 쪽에서 배운 것 두 가지>

  <15-1. 실행 중인 bash 스크립트를 고치면 안 된다>

  체인 스크립트(after_smoke.sh)를 돌아가는 도중에 수정했더니 같은 명령이 두 번 떴다.
  bash 는 스크립트를 **바이트 오프셋으로 게으르게** 읽는다. 앞부분에 150바이트를
  넣으면 실행 지점이 밀려서 이미 지난 줄로 되돌아가거나 줄 중간으로 뛴다.

  → 돌아가는 스크립트는 고치지 않는다. 고쳐야 하면 죽이고 다시 띄운다.
    (원래도 잠금 파일로 중복은 막았지만, 이건 **같은 프로세스 안에서** 두 번 실행된
     경우라 잠금으로 안 잡힌다.)

  <15-2. 프로세스를 죽일 때 `ps | awk '/patter[n]/'` 도 자기 자신을 잡는다>

  대괄호 트릭은 `pgrep -f` 의 자기매칭을 막아 주지만, **셸 래퍼**까지 막지는 못한다.
  Claude Code 가 명령을 `bash -c 'eval ...'` 로 감싸므로 그 cmdline 에 패턴이 그대로
  들어간다. 그래서 정리는 **명시 PID 트리**로만 한다 —
  부모 PID → ps --ppid 로 자식 → 다시 손자. 패턴 매칭은 확인용으로만 쓴다.
  (타 프로젝트 프로세스를 오살하지 않기 위해서도 이게 맞다.)

  <15-3. 캐시를 지운 직후가 가장 위험하다 — 옛 코드 프로세스가 다시 채운다>

  §13 의 수정으로 3.4GB 캐시를 지웠다. 그런데 그 시점에 **수정 전 코드로 이미 떠 있던**
  측정 프로세스가 살아 있었고, 그게 옛 순서로 만든 페이지를 계속 써 넣었다.
  새 코드로 뜬 스모크가 새 스탬프(v2)를 먼저 찍었으므로 **스탬프는 v2 인데 내용은
  섞인** 캐시가 된다. 스탬프 검사는 프로세스당 한 번뿐이라(`__stamp_checked`) 이미
  통과한 프로세스는 아무것도 막지 못한다.

    → 측정 스크립트는 학습 캐시를 쓰지 않는다. verify_u1 은 VERIFY_CACHE
      (기본 /tmp/verify-u1-cache)로 격리했다.
    → 데이터 경로 코드를 고치면 **옛 프로세스를 먼저 죽이고** 캐시를 지운다.


<16. `[TfCLG]\d+` 오탐 — 여섯 번째 (문자열 짝짓기)>

  1,200건 스캔의 N5 3건도 전부 오탐이었다.

    idx=411558   ") (C0 "
    idx=982051   "%string)] [T0 "

  옛 검사기:

    STR_NORM = re.compile(r'"[^"\n]*(?<![\w])[TfCLG]\d+[^"\n]*"')

  **정규화 이름을 요구하는 정규식으로 문자열을 찾으면 따옴표 짝이 어긋난다.**
  원본은

    Definition f2 (s : string) : Expression :=
      (ECall (ELit (C0 "io" )) (ELit (C0 "fwrite" )) [ELit (C0 s)]).

  이고, 정규식은 `"io"` 를 건너뛰고 **`") (f2 "` 라는 틈**을 문자열 하나로 잡는다.
  C0 도 f2 도 문자열 **밖**이다.

  고침: 리터럴을 **왼쪽부터 순서대로 짝지어** 다 찾고(`"(?:[^"\n]|"")*"`), 그 다음
  각 리터럴 **안에서만** 이름을 찾는다. 같은 프롬프트로 확인: 옛 정규식 탐지 →
  새 방식 무탐지.

  ※ 정규화 이름 오탐 여섯 번을 관통하는 교훈 하나 —
    **`[TfCLG]\d+` 는 정규화 이름의 충분조건이 아니다.**
    Coq 코드에 `f1` `f2` `C0` `T0` 같은 이름은 흔하다. 이 패턴으로 무언가를 판정할
    때는 항상 "이게 정말 우리가 만든 이름인가" 를 따로 확인해야 한다:
      · 이 tactic 이 도입한 이름인가 (introduced_names)
      · [STATE] 의 가설인가
      · 프롬프트에 선언이 있는가
      · (문자열·주석 검사라면) 리터럴 경계를 제대로 잡았는가


<17. 하위스텝 분포 — 설계대로 작동한다>

  계획 파일 앞 30,000건을 `_split_substeps` 로 직접 분해했다(프롬프트를 안 지으므로 즉시).

    하위스텝 개수   3: 26,871 (89.6%)   5: 2,363   7: 553   9: 132  …  23: 1
    전체 하위스텝   assert 34,242 · close 34,242 · final 30,000

    ★ sha1(sid) % n 으로 **선택된** 종류
        assert  10,305  34.4%
        close   10,171  33.9%
        final    9,524  31.7%

  `2k+1` 이 맞고(k=1 이 89.6%) 선택이 셋에 고르게 퍼진다.

  (검사기가 close 를 버리던 문제와 그 여파는 §9 에 적었다.)

  <17-2. close 에서 eqx 지시자가 하는 일 — 되는 경우와 안 되는 경우>

  `close` 는 assert 의 명제 `P` 를 goal 로 삼아 **검색을 다시 돌린다**
  (`_example_with_goal`, 캐시 없음). 찾는 것이 `P` 이고 `L` 의 명제가 `P` 이므로
  `eqx` 의 지시자 `1[⟦p⟧=⟦g⟧]` 가 **바로 이때** 발화한다 — α-동치가 성립하기 때문이다.
  하위스텝 설계와 `eqx` 의 지시자는 **같은 성질(강제성)의 두 얼굴**이다.

  ★ 단, 그건 **L 이 후보 풀에 있을 때만** 성립한다. 랭커는 풀에 없는 것을 올릴 수 없다.
    실측 85건 중 39건(45.9%)만 찾았고 나머지는 stdlib 라 풀에서 제외돼 있었다(§9).
    → 풀에 없으면 assert 스텝으로 물러선다.


<18. 표본 측정에 페이지 빌드를 쓰면 안 된다>

  캐시는 **파일(페이지) 단위**라 미스 한 번이 그 파일의 모든 proof×step 을 짓는다.
  학습은 한 파일을 여러 번 쓰므로 이득이지만, **표본 측정은 파일당 한두 건만** 쓰므로
  순 낭비다.

    페이지 빌드 경로   7분에 27건
    CACHE_MAX_PAGE=0   56초에 50건        ← 요청된 예제만 만든다

  verify_u1 · preflight_random · scan_prompts 의 기본값을 0 으로 바꿨다.


<19. 큰 프로젝트에서 검색 비용은 어디에 쓰이나 (CompCert)>

  "eqx 가 느려서 추론이 느려지지 않나" 를 확인했다. `scripts/bench_compcert_retrieval.py`
  로 한 스텝의 검색을 넷으로 나눠 잰다.

    ① 풀 조립      out-of-file + in-file premise 를 모으고 거른다
    ② 토큰화       `get_ids_from_sentence` — 풀 **전량**
    ③ tfidf        `tf_idf(query, docs)` — 풀 **전량** (O(N))
    ④ eqx 재랭킹    `structural_scores(stage1=5000)` — 상한이 걸린다

  <19-1. 콜드 (첫 스텝)>

                    CompCert(풀 2,135)   fourcolor(풀 2,858)
      ① 풀 조립        3.37 ms  13.4%      3.13 ms   7.9%
      ② 토큰화         5.36 ms  21.2%      9.43 ms  23.7%
      ③ tfidf         5.27 ms  20.9%      7.99 ms  20.1%
      ④ eqx          11.24 ms  44.5%     19.27 ms  48.4%
      합계           25.23 ms            39.82 ms

  ②+③ 이 tfidf 몫으로 42~44%, eqx 가 44~48%.

  <19-2. 워밍 후 — 추론의 실제 조건>

  증명 탐색은 **한 파일에서 수백 노드**를 돈다. `prem_stmt`/`prem_struct` 는
  `lru_cache(300k)` 라 첫 스텝에서만 파싱하고 이후는 조회다.

      CompCert    전체 15.49 ms · eqx 4.18 ms   → eqx 27.0%
      fourcolor   전체 18.91 ms · eqx 6.82 ms   → eqx 36.0%

  eqx 는 11.2 → 4.2 ms 로 **2.7배** 준다. tfidf 쪽은 질의마다 goal 이 새로 오므로
  캐시 이득이 없어, 워밍 후에는 **비 eqx 부분이 73%** 다.

  <19-3. 추론 전체에서>

  노드 처리는 Coq 300 ms 가 지배한다(memory: 7B 저조 원인은 추론속도가 아니다).

      노드 하나 ≈ 300 ms (Coq) + 15~19 ms (검색)
        검색 전체   5~6%

  <24-2. N2 — "같은 이름 두 번" 이 아니라 "같은 이름 · 다른 명제">

    idx=1681529   L9 · L6

  파 보니 중복 가드는 **정확히 작동하고 있었다**:

    [제외] find_spec     Lemma find_spec m x e {Hm:Ok m}: find x m = Some e <-> …
    [제외] find_spec     Lemma find_spec m x e : find x m = Some e <-> …
    [제외] add_spec1     (3번)   · remove_spec1 · remove_spec2 · add_spec2 · empty_spec
    [매핑] add_spec1'    ← 이름이 실제로 **다르다**(prime). 그래서 매핑됐다

  MMaps 계열은 같은 lemma 를 모듈마다 `add_spec1` / `add_spec1'` 로 재수출한다.
  이름이 다르니 각각 정규화되고, 명제는 **똑같다**:

    Lemma L6 m x e `{!Ok m} : find x (add x e m) = Some e.
    Lemma L6 m x e `{!Ok m} : find x (add x e m) = Some e.
    Lemma L6 m x e         : find x (add x e m) = Some e.

  `apply L6` 이 어느 것으로 읽혀도 맞는다 — **해롭지 않다.**
  위험한 것은 같은 이름에 **뜻이 다른 둘**이 붙는 경우다(그건 정리 이름 쪽에서
  이미 겪었고 `LAST_THM_DECL` 경로로 고쳤다).

  → 검사기를 `이름 → {명제 뼈대}` 로 바꿔 **집합 크기가 2 이상일 때만** 신고한다.
    바인더 표기 차이(`{Hm:Ok m}` vs `` `{!Ok m} ``)는 뼈대에서 지운다.
    같은 이름·같은 명제는 `N2b (무해)` 로 따로 센다.

  ※ 이번 하루에 검사기 오탐이 넷(다섯째~여덟째) 나왔다. 공통 원인은 하나다 —

    표지는 후보를 좁힐 뿐이고, "우리가 만든 것인가" · "뜻이 다른가" 를 따로 물어야 한다.
