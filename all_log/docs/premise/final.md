# 최종 방법론 — `structural` (학습 불필요)

> **상태**: **확정.** 랭킹 기준(각 2,500건)·프롬프트 기준(각 1,000건) 모두 측정 완료.
> 본학습에 실제로 넣는 스펙은 **§10** 에 있다.

---

## 0-0. ★ 두 가지 기준을 구분해야 한다

같은 실험도 **무엇을 "찾았다"로 볼 것인가**에 따라 수치가 크게 다르다.

| 기준 | 뜻 | 언제 쓰나 |
|---|---|---|
| **랭킹 기준** | 검색 점수 상위 k 안에 gold 가 있는가 | 랭커끼리 비교할 때 |
| **★ 프롬프트 기준** | gold 가 **실제로 프롬프트에 들어가는가** | **모델이 실제로 볼 수 있는가** |

둘이 벌어지는 이유는 **토큰 예산** 때문이다.

```
검색이 넘긴 premise      100개   (num_premises)
프롬프트에 들어간 것      10~20개  (premise_tokens 896 · hard_seq_len 2048 왼쪽절단)
★ 70~80% 가 잘린다
```

premise 길이 편차가 극심하다 — 최소 16 · p25 43 · 중앙 147 · 최대 928 토큰.
긴 것 하나(175토큰)가 짧은 것(20토큰) 여러 개를 밀어낸다.

**실측 차이 (TEST 예비 50건)**

| | 랭킹 기준 | 프롬프트 기준 |
|---|---|---|
| A · structural · ALL | 45.4% | **26.0%** |
| C · structural · ALL | 90.4% | **97.1%** |

A 는 절반으로 떨어지고 **C 는 오히려 오른다** — cut 을 세우면 그 명제가 정확히 goal 이라
최상위로 오기 때문에 예산 안에 확실히 들어간다.

> 아래 §2 의 표는 **랭킹 기준**이다. 프롬프트 기준 3스플릿 값은 §2-4 에 있고,
> **본학습이 실제로 쓰는 값은 프롬프트 기준**이다.

## 1. 지표 — 무엇을 재는가

분모는 **gold lemma 를 쓰고 그 lemma 가 후보 풀에 실제로 있는 스텝**.

| 지표 | 뜻 |
|---|---|
| **R@k** | 필요한 gold 중 **하나라도** 상위 k 안 |
| **ALL@k** | 필요한 gold 를 **전부** 상위 k 안 ← **판단은 이걸로** |

프롬프트에 상위 N 개만 들어간다. tactic 이 lemma 를 2개 쓰는데 하나만 들어가면 모델은
나머지를 지어내야 한다 — 불가능하다. TEST 에서 lemma 2개 이상 필요한 스텝이 **23.7%** 다.

**목표지표** = `A + (1-A)×C` — A 로 잡은 것에, 못 잡은 것을 assert 로 건진 것을 더한다.

### 2-4. ★ 프롬프트 기준 실측 (각 1,000건)

> **열 표기**
> · `@k[순위]` — 검색 점수 상위 k 안 (프롬프트 예산 **무관**)
> · `[프롬프트]` — 토큰 예산 안에 살아남아 **실제로 들어감** ← 실제 기준

#### A — 일반 goal (gold 가 프롬프트에 들어가는 비율)

| 랭커 | TRAIN `ALL[프롬프트]` | TEST `ALL[프롬프트]` | VAL `ALL[프롬프트]` |

★ **A 만 보면 `rrf` 가 TEST·VAL 에서 최선이다**(TRAIN 은 structural).
트리일치·정의이름 신호는 일반 goal 에서 오히려 **방해**가 된다.

#### C — cut 후 재검색

| 랭커 | TRAIN `ALL[프롬프트]` | TEST `ALL[프롬프트]` | VAL `ALL[프롬프트]` |
|---|---|---|---|
| tfidf | 66.9% | 72.7% | 73.5% |

★ **C 에서는 정반대로 크게 이긴다.** cut 을 세우면 그 명제가 정확히 goal 이라
최상위로 와서 예산 안에 확실히 들어간다.

#### 목표지표 `A + (1-A)×C`

| 랭커 | TRAIN `ALL[프롬프트]` | TEST `ALL[프롬프트]` | VAL `ALL[프롬프트]` |
|---|---|---|---|

| rrf | 90.2% | 91.7% | 89.5% |
| eqcov | 95.3% | 95.1% | 96.4% |
| **structural ← 확정** | **95.6%** | **95.3%** | **96.5%** |

**목표(90~95%)를 세 스플릿 모두 초과했다.**

> 위 네 줄은 **모두 cut 을 포함**한 값이다. 따라서 `tfidf` 줄은 "rango 원본"이 아니라
> *rango 의 검색 + 우리 cut* 이다. cut 없는 rango 원본은 바로 위 **A 표의 27.7%**(TEST).

#### `eqcov` vs `structural` — 차이는 TRAIN 에서만 보인다

목표지표 차이가 TEST +0.2pp · VAL +0.1pp · TRAIN +0.3pp 로 전부 노이즈 범위다.
그럼에도 `structural` 을 쓰는 이유는 **A(일반 goal)에서 세 스플릿 모두 앞서기** 때문이다
(TRAIN 46.6 vs 42.8 · TEST 31.1 vs 28.1 · VAL 24.1 vs 21.9). C 는 어차피 동률이다.

#### Definition 이름 신호는 기여가 없다

`eqcov`(신호 없음) vs `structural`(있음) 차이는 **TEST +0.2pp · VAL +0.1pp** 다.
정의 이름이 goal 에 나오면 그것은 **공유 토큰**이라 tfidf 가 이미 점수를 준다 —
정보가 겹친다. **제거를 권한다.**

#### ★★ 기존 rango 는 gold 가 프롬프트에 27.7% 밖에 안 들어간 상태로 SFT 했다

`tfidf` 가 기존 rango 의 검색이다. **lemma 를 쓰는 스텝의 72~76% 는 정답이 참조하는
lemma 가 프롬프트에 없는 채로 학습됐다.**

원래는 이름을 **외워서** 맞힐 수 있었으므로 치명적이지 않았다. v8 익명화가 그 우회로를
막으면서 문제가 드러난 것이다(익명화가 문제를 **만든** 게 아니라 **드러냈다** —
익명화 ON/OFF 로 읽기 가능성이 소수점까지 동일했다, details.md §2-2).

★ 검색·랭킹은 **정규화 이전**(원본 이름)에 돈다 — `collate_input` 에서 검색하고
`collate` 에서 정규화한다. 그래서 정규화가 랭킹에 영향을 주지 않는다.
정규화 후에도 goal 의 `ulp` 와 `Definition ulp` 가 **둘 다 `f1`** 이 되어 연결이 유지된다.

## 2-5. 담기 방식과 예산 (프롬프트 기준에서만 의미 있음)

**담기 방식** (TRAIN 1,500건 · 예산 896)

| 방식 | 중앙 개수 | gold 전부 포함 |
|---|---|---|
| greedy(기존) | 19 | 84.4% |
| **skip ★채택** | 20 | **84.9%** |
| knapsack | 27 | 78.8% |

`skip` = 넘치는 것을 건너뛰고 다음 것을 담는다(`break` → `continue`). 비용 0.
knapsack 은 개수를 42% 늘리지만 **긴 gold 를 버려서** 5.6pp 잃는다 — 개수가 목적이 아니다.
정규화를 먼저 해도 효과 없다(토큰 절감 1.8~2.9% 뿐).

**예산** (TRAIN 800건 · `hard_seq_len=2048` 왼쪽절단 반영)

| 예산 | 프롬프트 premise | 2048 초과율 | gold 포함 |
|---|---|---|---|
| 640 | 10 | 10.0% | 65.2% |
| **896 (현재)** | 12 | 15.2% | **72.7%** |
| 1200 | 13 | 23.8% | **74.2%** |
| 1600 | 13 | 36.1% | 74.2% |
| 2000 | 13 | 45.5% | 74.2% |

**1200 에서 포화된다.** 그 이상은 gold 를 하나도 더 못 넣으면서 2048 초과율만 올린다.
섹션 예산 합(3800)이 `hard_seq_len`(2048)을 넘어, 담은 것을 도로 버리기 때문이다.

→ **예산 896 유지 또는 1200. 진짜 해법은 `hard_seq_len` 증액**(학습 속도·메모리 대가).

## 3. 왜 이 조합인가

### 3-1. `eq` — 같은 신호가 상황에 따라 정반대로 작동한다

| 상황 | 질문 | 트리 완전일치 | 단방향 매칭 |
|---|---|---|---|
| 일반 goal (A) | "이 lemma 를 **쓸 수 있나**" | 거의 발화 안 함 → **무해** | 후보의 13~24% 통과, gold recall 50% → **해롭다** |
| assert 하위목표 (C) | "이 lemma 가 **바로 그것인가**" | 정확히 그 질문 → **강력** | 느슨해서 약함 |

이전에 만든 `struct`(완전일치 + 단방향매칭)는 A 에서 ALL@50 이 45.4% → 18.2% 로 무너졌다.
**단방향 매칭을 빼고 완전일치만 남긴 것이 `eq`** 이고, 그래서 A 를 안 해치면서 C 를 살린다.

### 3-2. `cov` — 길이 정규화 문제를 겨눈다

TF-IDF 는 문서가 길수록 점수가 낮아진다. 진단에서 실패 161건 중 **58건**이 이 때문이었다.

```
질의   { eq x y } + { ~ eq x y }
1위    Definition eq := peq.              토큰  3개  tfidf 5.0821
gold   forall x y, {eq x y}+{~eq x y}.    토큰 13개  tfidf 2.7788   ← 12위
```

**질의 포함률**(질의 토큰 중 몇 %를 premise 가 담고 있나)은 문서 길이로 나누지 않아
이 편향이 없다. C 에서 ALL@50 을 90.4% → 92.2% 로 올린다. 대신 A 를 1.5pp 깎는다.

## 4. 두 가지 선택지

| | **eq** | **eqcov** |
|---|---|---|
| A ALL@50 | **45.4%** (rrf 와 동일) | 43.9% |
| C ALL@50 | 90.4% | **92.2%** |
| 목표지표 ALL@50 | 94.8% | **95.6%** |
| 목표지표 ALL@20 | 92.5% | **93.2%** |

**`eq` 는 `rrf` 를 파레토 지배한다** (A 동일 · C 우수). 안전한 선택이다.
**`eqcov` 는 합성 지표가 가장 높다.** A 를 조금 내주고 C 를 더 얻는다.

프롬프트에 50개를 넣는다면 `eqcov`, A 자체를 최대화하고 싶다면 `eq` 다.
**현재 권고는 `eqcov`** — 목표지표가 최고이고 ALL@20 에서도 앞선다.

GBDT 는 오프라인 jsonl 평가에서 R@50 88.6% 였지만 실제 파이프라인에서는 학습 때
후보 400개 / 추론 때 2000개라 순위 백분위 척도가 어긋나 무너졌다(자세히는

그래도 `eqcov` 에 못 미치고 학습·유지 비용이 든다.

**성능이 비슷하면 단순한 쪽이 낫고, 여기서는 단순한 쪽이 더 좋기까지 하다.**

## 6. 파이프라인 전체 — B 를 곱해야 한다

목표지표는 "검색이 잡거나, assert 로 건진다" 를 잰다. 그런데 **assert 를 만들 수 있어야**
건질 수 있다. B(assert 생성 성공률)를 곱한 것이 실제 값이다.

```
전체 = A + (1-A) × B × C
     = 45.4% + 54.6% × B × 92.2%
```

| B | 전체 |
|---|---|
| 85.2% (evar 구제 전) | 88.3% |

### 10-4. cut 품질 게이트

`build_cuts.py` 는 아래를 **하나라도** 어기면 cut 을 **버린다**(→ ③ hopeless 로 강등).

| 검사 | 이유 |
|---|---|
| `assert (` / `eassert (` 로 시작 | 형태 |
| `as H_asrt<n>.` 이름표 존재 | 없으면 문장이 잘린 것 |
| `{` `}` 증명 블록 존재 | 없으면 잘린 것 |
| 괄호 개수 균형 | 없으면 잘린 것 |
| **≤ 128 토큰** (`out_tokens`) | 넘으면 collator 가 라벨을 잘라 깨뜨린다 |

> 예전 코드는 `cut_tac[:800]` 으로 **잘랐다**. 잘린 assert 는 Coq 문법이 깨지므로
> 모델이 깨진 문자열을 외운다. 자르지 말고 버리는 것이 맞다.
> 실측 강등 **188/5,466 = 3.4%** (183건이 128토큰 초과).

### 10-5. 채택하지 않은 것

| 방법 | 이유 |
|---|---|
| GBDT 랭커 | structural 보다 낮고 학습·배포 비용 발생 (§5) |
| Contrastive 크로스인코더 | 이득 없음, 추론 비용 큼 (`contrastive.md`) |
| 신규 신호 (hyp/sub/cooc/nsub) | 차이가 노이즈 범위 |
| stdlib 이름 살려두기로 환각 감소 | **효과 없음.** 익명화 OFF/ON 환각률 7.9% vs 8.0% |
| `hard_seq_len` 2048 → 3072 | 효과는 크나(gold +14.6pp) 메모리·속도 비용 → 이번 학습은 2048 유지 |

**stdlib 프로브** — 모델이 stdlib lemma 명제를 아는지 직접 물었다.
stdlib 이름 F1 **0.292** vs 가짜 이름(대조군) F1 **0.291**. **모른다.**
그래서 "stdlib 이면 검색 없이 gold 를 그대로 써도 된다"는 전제는 성립하지 않고,
stdlib 도 ①②③ 판정을 똑같이 거친다.
