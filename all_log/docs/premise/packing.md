# premise 담기 — greedy · skip · knapsack · **hybrid(확정)**

검색이 고른 premise 를 **프롬프트에 어떤 순서·기준으로 담을 것인가**. 예산이 제한돼 있어
전부는 못 넣는다.

---

## 0. 용어

| 용어 | 뜻 |
|---|---|
| **premise** | 프롬프트 `[PREMISES]` 에 넣는 기존 lemma·정의 목록. 모델이 tactic 을 만들 때 참고한다 |
| **예산 (premise_tokens)** | `[PREMISES]` 에 쓸 수 있는 토큰 수. 현재 **896** |
| **담기(packing)** | 검색 순위대로 늘어선 premise 를 예산 안에 골라 넣는 일 |
| **hard_seq_len** | 프롬프트+정답 전체 토큰 상한. 현재 **2048**. 넘으면 **앞에서부터** 잘린다 |
| **gold 포함** | 그 스텝의 정답 tactic 이 쓰는 lemma 를 **전부** 프롬프트에 넣었는가 |

---

## 1. 왜 문제인가

```
검색이 넘긴 premise      100개  (num_premises)
프롬프트에 들어가는 것    10~22개
★ 70~80% 가 잘린다
```

**premise 길이 편차가 극심하다.**

```
최소 16 · p25 43 · 중앙 147 · p75 223 · 최대 928 토큰
```

실제 예 (예산 896, 검색 100개):

```
  1위   43토큰 (누적  43) ✓  Lemma gpaco5_unfold clo r rg: ...
  9위   20토큰 (누적 317) ✓  Lemma gpaco5_base clo r rg: r <5= gpaco5 clo r rg.
 12위  108토큰 (누적 472) ✓  Lemma _paco_pre8: forall T0 T1 T2 ...
 13위  118토큰 (누적 590) ✓  Lemma _paco_pre9: ...
 16위  145토큰 (누적 786) ✓  Lemma _paco_pre11: ...
 17위   20토큰 (누적 806) ✓  Lemma gpaco5_def_mon clo : ...
 18위  175토큰 (누적 981) ✗ 여기서 끝
```

`_paco_pre8/9/11` 셋이 371토큰(예산의 41%)을 먹었다. 20토큰짜리 짧은 lemma 여럿을
밀어낸 셈이다.

---

## 2. 네 가지 방식

### ① greedy — 순위대로 담다가 넘치면 **중단**

```python
for s in ss:
    n = len(tokenize(s))
    left -= n
    if left < 0:
        break          # ← 여기서 끝
    out.append(s)
```

**기존 방식.** 가장 단순하고, 검색 순위를 그대로 존중한다.
문제는 **긴 것 하나를 만나면 그 뒤를 전부 포기**한다는 것이다. 위 예에서 18위(175토큰)
때문에 19위 이후의 짧은 lemma 들이 전부 버려진다.

### ② skip — 넘치는 것은 **건너뛰고** 다음 것을 시도

```python
for s in ss:
    n = len(tokenize(s))
    if n > left:
        continue       # ← 이것만 건너뛴다
    left -= n
    out.append(s)
```

**한 줄 차이다** (`break` → `continue`). 순위는 그대로 존중하되, 예산에 안 맞는 것만
건너뛴다. 뒤의 짧은 것들이 살아남는다.

### ③ knapsack — **가치 ÷ 무게** 비로 담는다

```python
# 가치 = 순위 점수(앞일수록 높다), 무게 = 토큰 수
items = sorted(range(n), key=lambda i: -((n - i) / tokens(i)))
for i in items:
    if tokens(i) <= left:
        left -= tokens(i)
        out.append(i)
```

배낭 문제(knapsack problem)의 그리디 근사다. "**같은 예산에 최대한 많은 가치**" 를
노린다. 짧으면서 순위가 높은 것을 우선한다.

**순위를 뒤섞는다** — 100위짜리 20토큰이 5위짜리 300토큰보다 먼저 담길 수 있다.

### ④ hybrid — 상위 K 는 무조건, 나머지는 배낭  ★ 확정안

```python
head, left = _greedy(all_idx[:topk], allowance, skip=True)   # 상위 4개: 순위 존중
tail, _    = _knap(all_idx[topk:], left)                     # 나머지: 가치÷무게
picked = head + tail
picked.sort()                                                # 원래 순위 순서로 복원
```

`PREMISE_PACK=hybrid` · `PREMISE_PACK_TOPK=4`.

**knapsack 의 유일한 약점을 겨눈다.** knapsack 은 개수를 크게 늘리지만(19→30) 가끔
**긴 gold 를 버린다** — 300토큰짜리 핵심 lemma 대신 20토큰짜리 여럿을 넣는 식이다.
상위 4개는 배낭 계산에서 빼고 무조건 넣으면 그 사고가 막히고, 남은 예산에서만
배낭이 개수를 늘린다.

`K=4` 인 이유: K 를 키울수록 greedy 에 가까워지고, 줄일수록 knapsack 에 가까워진다.
K=2·4·8 을 재서 4 가 세 스플릿 평균이 가장 높았다.

## 3. 실측

**분모: 각 스플릿에서 gold lemma 가 후보 풀에 있는 스텝 · 예산 896토큰**

| 방식 | TRAIN 개수 | TRAIN gold | TEST gold | VAL gold |
|---|---|---|---|---|
| ① greedy(기존) | 19 | **84.4%** | **63.1%** | **55.6%** |
| ② skip | 20 | 84.9% (+0.6p) | 65.5% (+2.4p) | 59.5% (+3.9p) |
| ③ knapsack | 27~30 | 78.8% (**−5.6p**) | 70.8% (**+7.7p**) | 70.7% (**+15.1p**) |
| **④ hybrid K=4 ★확정** | 25~28 | **83.5% (−0.9p)** | **72.1% (+9.0p)** | **71.0% (+15.4p)** |
| ⑤ 정규화+greedy | 19 | 84.9% | 63.7% | 57.8% |
| ⑥ 정규화+skip | 20 | 84.9% | 64.9% | 59.9% |
| ⑦ 정규화+knapsack | 27~31 | 78.8% | 70.2% | 71.1% |

(판정 대상: TRAIN 179건 · TEST 168건 · VAL 232건)

### 읽는 법

**skip 은 세 스플릿 모두 양수다** (+0.6 / +2.4 / +3.9p). 비용 0, 위험 0.

**knapsack 은 스플릿마다 다르다** — TRAIN −5.6p, TEST +7.7p, VAL +15.1p.
평균 +5.7p 지만 TRAIN 에서만 손해다. TRAIN 은 baseline 이 84.4% 로 이미 높아
(쉬운 케이스가 많아) 개선 여지가 작았던 것으로 보이며, **원인 규명이 필요하다.**

knapsack 이 지는 기전은 분명하다: **긴 gold 를 버린다.** 가치/무게 비로 담으면
300토큰짜리 중요한 lemma 대신 20토큰짜리 여럿을 넣는다. 개수는 늘지만(19→30)
정작 필요한 것을 놓칠 수 있다.

**hybrid 가 그 기전을 정확히 막는다.** TRAIN 손실이 −5.6p → **−0.9p** 로 줄고
TEST·VAL 이득은 오히려 커졌다(+7.7→+9.0p, +15.1→+15.4p).
**세 스플릿 평균 +7.8p** 로 네 방식 중 최선이라 이것을 확정했다.

> ★ **개수가 아니라 gold 포함률이 지표다.** knapsack 이 개수 30개로 가장 많지만
> TRAIN 에서 지는 이유가 그것이다. 개수 열은 진단용으로만 본다.

**정규화를 먼저 하는 것(④⑤⑥)은 효과가 거의 없다.** lemma·타입 이름을 `L0`/`f1` 로
바꿔도 토큰 절감이 **1.8~2.9%** 뿐이다. premise 본문 대부분(`clo`, `r`, `rg`, 연산자)은
정규화 대상이 아니고, `f1` 이 `to_lu` 보다 토큰이 많은 경우도 있다.

## 4. 더 큰 문제 — 담기 이전에 `hard_seq_len` 이 자른다

섹션 예산 합이 상한을 넘는다.

```
premise 896 + proof 640 + state 1024 + script 512 + out 128 + types 300 + defs 300
= 3800   >   hard_seq_len 2048
```

초과분은 `truncation_side="left"` 로 **맨 앞([PREMISES])부터** 잘린다.
실측(TRAIN): **17.6% 의 예제가 `[PREMISES]` 섹션을 통째로 잃는다.**
(검색이 100개를 넘겼는데 프롬프트에는 하나도 없다.)

**분모: TRAIN 700건 중 gold 판정 대상 55건**

| 설정 | `[PREMISES]` 소실 | premise 중앙 | gold 포함 |
|---|---|---|---|
| 현재 | 17.6% | 14 | 61.8% |
| proof 640→256 | 10.0% | 15 | **70.9%** |
| state 1024→640 | 17.1% | 14 | 61.8% |
| proof+state 축소 | 8.1% | 16 | 70.9% |
| **hard 2048→3072** | **0.9%** | 17 | **76.4%** |
| hard 3072 + premise 1200 | 3.1% | **20** | **78.2%** |

**담기 방식을 바꾸는 것보다 이쪽 효과가 훨씬 크다** (+14.6pp vs +0.6~15p).

  · `hard_seq_len` 2048 → 3072 — 소실 17.6% → 0.9%. 대가는 어텐션 연산 ~2.25배
  · `proof_tokens` 640 → 256 — 공짜로 +9.1pp. 비슷한 증명 섹션을 줄인다
  · `state_tokens` 축소는 효과 없음 — state 는 원래 짧다

## 5. premise 예산 자체를 늘리면?

**분모: TRAIN 800건 · 2048 왼쪽절단 반영**

| 예산 | 프롬프트 premise | 2048 초과율 | gold 포함 |
|---|---|---|---|
| 640 | 10 | 10.0% | 65.2% |
| **896 (현재)** | 12 | 15.2% | 72.7% |
| 1200 | 13 | 23.8% | **74.2%** |
| 1600 | 13 | 36.1% | 74.2% |
| 2000 | 13 | 45.5% | 74.2% |

**1200 에서 포화된다.** 그 이상은 gold 를 하나도 더 못 넣으면서 2048 초과율만 올린다 —
담은 것을 `hard_seq_len` 에서 도로 버리기 때문이다.

★ 컨텍스트가 길수록 **어텐션이 희석**될 수 있는데, 이 실험으로는 못 잰다.
무관 premise 가 늘어 모델이 헷갈리는 효과는 **학습·평가로만** 확인된다.

## 6. 현재 결론

| 항목 | 결정 | 근거 |
|---|---|---|
| **담기 방식** | **`hybrid` K=4 확정** | 세 스플릿 평균 **+7.8p**, TRAIN 손실 −0.9p 뿐 |
| greedy | 불채택 | 긴 premise 하나에 막혀 뒤를 통째로 버린다 |
| skip | 불채택 | 안전하지만 이득이 작다(+0.6/+2.4/+3.9p) |
| knapsack 단독 | 불채택 | TEST/VAL 크게 이기나 TRAIN −5.6p (긴 gold 를 버린다) |
| 정규화 먼저 | 불채택 | 토큰 절감 1.8~2.9% 뿐 |
| premise 예산 | **896 유지** | 1200 에서 포화, 그 이상은 2048 초과율만 올린다 |
| **hard_seq_len** | **2048 유지 (다음 실험)** | 소실 17.6%→0.9%, gold +14.6pp — **가장 큰 지렛대**지만 어텐션 연산 2.25배 |
