# GBDT 의 문제 — 오프라인 86.6% 가 실제 파이프라인에서는 왜 안 나오나

`gbdt.md` 는 GBDT 가 **어떻게 동작하는지**를 적었다. 이 문서는 **무엇이 문제인지**를 적는다.

> 모든 표에 **분모**를 붙였다. 지표는 두 가지다.
>
> · **R@k** — 그 스텝에 필요한 gold lemma 중 **하나라도** 상위 k 안에 든 스텝의 비율
> · **ALL@k** — 필요한 gold 를 **전부** 상위 k 안에 넣은 스텝의 비율
>
> 프롬프트에는 상위 N 개만 들어간다. tactic 이 lemma 를 2개 쓰는데 하나만 들어가면
> 모델은 나머지를 **지어내야** 하므로 불가능하다 → **실제로 중요한 것은 ALL@k** 다.
> TEST 에서 lemma 를 2개 이상 쓰는 스텝이 **24%** 라 이 차이가 실제로 크다.

## 2. ★ 새로 발견한 문제 — 학습과 추론의 후보 집합이 다르다

GBDT 를 **처음으로 실제 파이프라인 경로에서** 돌려 봤다(`eval_retrieval.py`). 오프라인
jsonl 평가와 결과가 달랐다.

**분모: gold lemma 를 쓰고 그 lemma 가 후보 풀에 있는 TEST 스텝 40건 (표본 작음, 예비)**

| 랭커 | R@1 | R@20 | R@50 | ALL@20 | ALL@50 |
|---|---|---|---|---|---|
| tfidf | 0.0% | 35.0% | 47.5% | 25.0% | 35.0% |
| RRF | **17.5%** | 37.5% | 52.5% | 32.5% | 40.0% |
| GBDT | **2.5%** | **45.0%** | **57.5%** | **35.0%** | **42.5%** |

**R@20/R@50 은 GBDT 가 이기는데 R@1 은 RRF 의 1/7 이다.** 오프라인 평가에서는
GBDT 가 R@10 에서도 RRF 를 크게 이겼다(70.6% vs 37.1%). 앞뒤가 안 맞는다.

### 2-1. 원인 — 순위 백분위의 척도가 달라진다

특징 36개 중 24개가 **사례 내 순위 백분위**와 그 RRF 변환이다(`gbdt.md` §4). 백분위는
**후보 집합 크기에 의존**한다.

```
학습 (dump_retrieval_features.py, CAP=400)
    후보 = tfidf 상위 400개  +  gold (400 밖이어도 강제로 넣음)
    tfidf 순위 100위인 premise  →  백분위 100/400 = 0.25

추론 (eval_retrieval.py, stage1=2000)
    후보 = tfidf 상위 2000개  (gold 강제 삽입 없음)
    tfidf 순위 100위인 premise  →  백분위 100/2000 = 0.05
```

**같은 premise 가 학습 때 0.25, 추론 때 0.05 로 들어간다.** 트리는 "백분위 0.25 보다
작은가?" 같은 임계값 규칙을 400개 척도에서 배웠는데, 추론에서 척도가 5배 늘어난 것이다.
상위권이 특히 망가진다 — 그래서 **R@1 이 무너졌다.**

### 2-2. 두 번째 원인 — 학습에는 gold 가 항상 있었다

```python
# dump_retrieval_features.py
keep = list(order)                 # tfidf 상위 CAP
for j in gset:                     # ★ gold 는 CAP 밖이어도 반드시 넣는다
    if j not in oset:
        keep.append(j)
```

학습 사례는 **반드시 positive 를 포함**한다. 추론에는 그런 보장이 없다 — gold 가 상위
2000 밖이면 그 사례에는 positive 가 아예 없다. 모델은 "이 집합 어딘가에 정답이 있다" 는
전제로 배웠는데 추론에서는 그 전제가 깨진다.

### 2-3. 세 번째 원인 — IDF 와 열별 최대 정규화

  · C' 의 IDF 를 **그 사례의 후보 집합 안에서** 계산한다 → 400개 기준과 2000개 기준이 다르다
  · 특징을 `열별 최대값` 으로 나눈다 → 후보가 많아지면 최대값이 커져 전체가 눌린다

### 2-4. 검증 실험 (진행중)

추론 후보 수를 학습과 같은 **400** 으로 맞추면 GBDT 의 R@1 이 회복되는지 본다.
회복되면 원인 확정이고, 고치는 방법은 둘 중 하나다.

  ⑴ 추론을 학습에 맞춘다 — `stage1=400` 고정 (간단하지만 상한이 낮아진다)
  ⑵ 학습을 추론에 맞춘다 — 덤프를 `CAP=2000`, gold 강제삽입 없이 다시 뜬다 (정석)

> ★ ⑵ 가 옳다. 학습이 추론 조건을 흉내내야지 그 반대가 아니다. 다만 덤프가 5배 커진다.

## 4. 별개의 문제 — assert 하위목표에서는 GBDT/RRF 둘 다 답이 아니다

### 4-1. 증상

assert 로 쪼갠 뒤의 하위목표는 **goal 이 곧 lemma 의 문장**이다. 그러면 그 lemma 가
1위로 나와야 마땅한데 그렇지 않다.

**분모: gold 가 후보 풀에 있고 gold 문장을 파싱할 수 있는 TEST 스텝 250건.
질의 = gold L 의 결론 그대로 (상한 설정 — 실제보다 유리하게 잡은 것)**

| 랭커 | R@1 | R@5 | R@10 | R@50 |
|---|---|---|---|---|
| tfidf | 35.6% | 62.4% | 74.0% | 87.6% |
| **구조우선** | **74.8%** | **87.2%** | **90.4%** | **92.8%** |

### 4-2. 왜 tfidf 가 지는지 — 실제 사례 넷

**① 구조를 못 봐서 진다** — 토큰이 완전히 같다

```
context    E, E', E'' : Ens,   EQ E' E''
원래 goal  IN E E''                       ← 이 lemma 는 top50 밖이었다
assert 후  goal = IN E E''                 질의 토큰 ['IN','E',"E''"]

1위  IN_sound_left  : forall E E' E'', EQ E E'   -> IN E E' -> IN E E''   tfidf 9.9214
2위  IN_sound_right : forall E E' E'', EQ E' E'' -> IN E E' -> IN E E''   tfidf 9.9214  ← gold
```

`left` 와 `right` 는 **변수가 어디에 놓이냐**만 다르다. 토큰 가방으로는 원리적으로
구별 불가능하고, gold 가 2위인 것은 순전히 정렬 순서 때문이다.

**② 길이 정규화로 진다** — 짧은 문서가 이긴다

```
assert 후  goal = { eq x y } + { ~ eq x y }     질의 토큰 ['eq','x','y','+','~','eq','x','y']

1위   eq      : Definition eq := peq.            토큰  3개  tfidf 5.0821
gold  eq_dec  : forall x y, {eq x y}+{~eq x y}.  토큰 13개  tfidf 2.7788   ← 12위
```

`eq` 하나뿐인 3토큰 정의가, 질의를 **정확히 담고 있는** 13토큰 gold 를 이긴다.

**③ 괄호 위치가 달라도 토큰은 같다**

```
assert 후  goal = x * (y * z) == y * (x * z)

1위   ARmul_assoc1 : (x * y) * z == (y * z) * x     tfidf 4.8550
gold  mulRCA       : x * (y * z) == y * (x * z)     tfidf 4.6567   ← 3위
```

**④ 질의 토큰이 너무 흔하다**

```
gold       Definition ptr64 := true.
assert 후  goal = true      질의 토큰 ['true']   tfidf 0.0000   ← 12,390위
```

`true` 는 수천 개 premise 에 나와 IDF 가 0 에 수렴한다.

**원인 분류 (250건 중 1위가 아닌 161건)**

| 원인 | 건수 |
|---|---|
| 구조를 못 봄 (토큰 같은데 배치 다름) | 80 |
| 길이 정규화 — 짧은 문서가 이김 | 58 |
| 질의 토큰을 이긴 쪽이 더 많이 포함 | 14 |
| 완전 동점 | 9 |

### 4-3. 고치는 방법 — 질문을 바꾼다

네 원인 모두 **TF-IDF 가 토큰 가방**이라서 생긴다. assert 하위목표에서 물어야 할 것은
"토큰이 겹치나" 가 아니라 **"항 트리가 같은가"** 다.

```python
score = 3.0 * [premise 결론 트리 == 질의 트리]        # 완전 일치
      + 1.0 * [premise 를 패턴으로 두면 질의에 맞음]     # 단방향 유니피케이션
      + tfidf / max(tfidf)                          # 동점 깨기
```

세 줄로 R@1 이 **35.6% → 74.8% (+39pp)** 다. 남은 25% 는 파서가 못 읽는 premise
(notation, mathcomp 표기)이며, 여기서도 **파서 recall 이 상한**이다.

### 4-4. ★ 같은 신호가 상황에 따라 정반대로 작동한다

| 상황 | 질문 | 적용가능성 신호 효과 |
|---|---|---|
| 일반 goal | "이 lemma 를 **쓸 수 있나**" — 느슨. 후보의 13~24% 가 통과 | **R@50 −9pp (해롭다)** |
| assert 하위목표 | "이 lemma 가 **바로 그것인가**" — 엄격 | **R@1 +39pp (좋다)** |

일반 goal 에서는 gold recall 이 46~50% 라, 판정 못 받은 gold 가 통과한 50~100개
아래로 밀린다. assert 하위목표에서는 goal 이 lemma 문장 자체라 **완전 일치**를 물을 수
있고, 그건 훨씬 선택적이다.

**교훈: 랭킹 신호는 그 자체로 좋거나 나쁘지 않다. 어떤 질문에 쓰느냐가 결정한다.**
