[A. filtering + 학습에 대해서]

[0. 현황]

요구 사항들을 지키면서.

[1.개요]

지금 진행하는 applicability 실험은 왜 하는가?

[지금 성능이 좋지 않은 이유]

(1) premise retrieval 의 성능이 좋지 않다.
(retrieved된 lemma 목록에 gold lemma를 포함하는 확률이 높지가 않다.)
(2) 학습 방법이 잘못 되어서 
(3) premise retrival 할때 그 대상을 built-in을 포함하지 않아서 엉뚱한 lemma를 가지고 오는 경우가 있다.
사실 이렇게 하는 이유는 built-in 의 양이 너무 많기 때문이다.

[2. 해결 방법 + 알고리즘]
나는 이거 아래와 같이 해결 하려고 한다.

(1) 일단 built-in 까지 포함해서 더 큰 추출 대상 premise set을 만든다.
근데 이렇게 하면 더 커질 것이기 때문에
gold를 가지고 올 확률이 더 높아질 것이다.
(2) 그런데 이렇게 하면 당연히 집합이 엄청 커지겠지?
그래서 applicability 기준으로 필터링을 할 것이다.
적용 가능성을 가지고 filtering을 할 것이다.
이때 4가지 유형을 볼 것이다. 
<apply 계열 (eapply L, apply, ...) +
apply in 계열 (apply L in H...) +
rewrite 계열 +
rewrite in 계열>
지금 계열 이름은 우리는 이런 convention을 쓰고 있다.

그런데 이렇게 하면 각자 4개의 premsises set이 다른 것이기 때문에
(3) 그리고 각각의 channel에 대해서 랭킹을 새롭게 구현해야한다.
그걸 연구하고 있는게 r11, r12 이런거다.
(4) 나중에 그렇게 한 다음에 sft를 할거다. 
지금까지와는 다르게 [Premises] 섹션을 앞서 말한 4개 계열 +
기존의 tf-idf 방식을 유지하는 계열
이렇게 5개 계열로 따로 따로 분리할 예정이다.
각각은 몇 개씩 유지할지는 모르겠는데 10 ~ 20개 정도?
그렇게 한 다음에 sft를 할거다. 

일단은 지금은 channel별 applicability이랑 ranking쪽에 집중한다.
일단 이게 높게 나와야 (4)를 하는 의미가 있기 때문이다.

applicability + ranking의 성능이 높게 나와서 gold lemma를 100프로 맞추면 
좋겠지만 그건 불가능한 경우가 있다. 
그러면 그 경우는 gold를 억지로 주입해서 sft를 만들어야 할건데, 
(답이 프롬프트에 없는데 맞추게 하는 이상하기 때문에)
~ top 20 에서 랜덤하게 끼워넣는 것을 고려해봐야 할거 같은데 이건 뭐
sft를 할때 생각해보기로 하자.

[3. 성능 요구 사항]
- 데이터: applicability filtering을 했을때 gold lemma를 포함하는 확률은 
거의 100을 유지해야 한다. 이건 거의 끝난 것으로 아는데,
기회가 되면 train, test, val 에서 많이 실험을 해보면 좋을거 같다.
그리고 지금 apply rewrite 비율이 높고, 
apply-in, rewrite-in은 비율이 낮은 것으로 알고 있는데 
비율이 낮아도 성능 병목이 될 수 있으니까, 
rewrite-in, apply-in 개수도 많이 가지고 테스트 셋에 넣어줘.
충분히 실험할 수 있도록

- 척도: 각 channel 별로 gold가 @10 이내 + @20 이내로는 들어오는 것이 좋다.
예를 들면 apply L이 gold tactic 일때 
apply channel에 복원된 premises 들에
gold lemma인 L이 높은 상위에 있어야 한다.

계속해서 랭킹을 보여줄때, 각 split 별로 gold tactic에 대응되는
chaneel이 @10, @20, @50에 gold lemma를 포함할 확률을 보여준다.
lemma가 여러개이면 하나라도 포함 + 다 포함을 구분해서 보여준다.
일단은 프롬프트에 들어가는지 신경쓰지 않고 premises 랭킹으로만 본다.

retrieval이 너무 무거워지면 실제로 추론을 할때 너무 느려서 
탐색 노드가 많지 않을 확률이 있다. 그렇기 때문에 너무 느리면 안된다.
시간도 신경써서 최적화를 해줘

- 랭킹은 채널 별로 좋은 것을

- 지금 ap, in, rw, rwh은 다 알고리즘은 개발중이고,

- 단 여기서 측정 대상은 지금 프롬프트에 들어가는 context, 타입 정의, 함수 정의를 
제외한 retrieval 대상인 premises 들을 사용하는 tactic 들에 대해서만 성능을 체크한다.

- 가중치가 너무 많으면 오버피팅 문제가 있을 수 있다.
그래서 가중치 개수가 너무 많으면 안된다.

- 너무 알고리즘이 지저분하면 안되니까 신경써서 알고리즘 설계를 해줘.

- 만약 가중치를 꼭 너야 한다면 trainable 하게 만든다.
만약 통계량 기반이라면 train split에서 학습한 다음에

- PL 적으로 예쁘고, 수학적으로 예쁘면 좋다.

- 물론 성능이 최우선이기는 하지만 너무 더려우면 논문을 쓰기에 좋지 않다.

- 알고리즘이 너무 느리면 안된다.

[B. sft에 대해서]
이전에 언급했듯이 알고리즘은 4단계로 구성이 되어 있다.
만약 ranker + applicability 필터가 완성이 되어 있다면 다음 단계로 나아가야 한다.
이에 대한 스팩을 정리한다. 

[0. 취지]
- 기존 학습 방법은 프롬프트에 없는 lemma도 사용해서 출력으로 내놓으려고 하는데, 
나는 그것을 막기 위해서 꼭 사용해야 하는 lemma가 답이 있는 경우에만 sft를
만들려고 함.

[1. 포름프트 구성]
- 크게 보면 아래와 같음
현재 context(=goal + hyps)
-> rango 처럼 비슷한 proof state를 추출.
-> 지금까지 정보를 바탕으로
타입이랑 함수 정의를 추출 / 익명화 이전을 기준으로 premises들을 추출. 자세한 방법은 아래 참조
                            (applicability + ranking)
-> 다 뽑았으면 이름 + 타입 정보 + 생성자들을 정부 익명화를 진행한다.
-> 지역 가설도 익명화 해야 하나? 이름을 외우지 않게 외울 수 있으면 좋겠는데. 
익명화를 할때 stdlib는 익명화 하지 않음. 그냥 외워도 된다고 가정함.

- 기존에는 [premises] 밑에 premise 50개? 100개였나 암튼 많이 넣었는데
tf-idf를 사용해서, 이는 문제가 있었다 (위에 이미 언급했음)

- 그래서 이걸 다음과 같이 
[PremisesForApply], [PremisesForAppyIn], [PremisesForRewrite],
[PremisesForRewriteIn], [Otheres]
이렇게 구분해서 5개로 분리하고, 앞의 4개의 체널은 각각이 사용하고 있는 랭커로 채워넣고, 
뒤에는 rango가 사용하고 있던 tf-idf를 사용해서 채워넣는다.
각각의 섹션에 10개랑 20개 중 하나를 택해서 상위로 채우려고 하는데 뭐가 좋을지는 잘 모르겠어.

[2. sft 학습 프레임 워크]
- 학습은 기존처럼 아래 구성을 따라해
(프롬프트 -> gold tactic) 예측.
gold tactic이 지역 가설을 쓰거나
그런데 당연하게도 retrieval은 완벽하지 않기 때문에
프롬프트에  정답이 없을 수도 있다. 그래서 아래와 같이 경우를 나누는 것이 중요하다.

case A = 정답 lemma 같은 외부 참조가 프롬프트에 있음>
그러면 prompt -> gold tactic sft를 학습.
+ 물론 apply _L0 처럼 익명화된 상태로 gold tactic을 예측하게 만들어야 하고.
그런데 이렇게 해도 답이 외워져 버릴 수 있어서, 아래 처럼 [3. ] 항목처럼 바꾸는 것도
괜찮지 않을까 싶은데 그건 좀 있다가 더 자세히 서술해보겠다.

case B = gold lemma가 포름프트에 없음>
이럴때는 그냥 대답을 외워 버리는 것이 될 수 있기 때문에, 
gold를 랜덤하게 프롬프트에 억지로 넣어준다.
만약 premise 20개를 복원해서, 
12개가 프롬프트에 들어간다고 하면, 랜덤하게 1/12 확률로 해서 하나의 정답이 아닌
lemma를 걷어 낸 다음에 걔를 정답으로 바꾼다. 
여기서 주의할 점은 지금 channel 별로 premises를 다르게 잡아주고 있는데, 
정확한 channel을 잡아서 주입해줘야 한다. 예를 들면 apply L in H 얘가 gold tactic인데
[PremisesForAppyIn] 안에 L이 없으면 얘한테 주입을 해줘야 한다는 의미이다.
channel 별로 다르게 해야 한다는 사실을 계속 기억하도록해.
이렇게 넣어주면 동일하게 prompt -> gold tactic sft를 학습. 으로 학습이 가능하다.

[3. gold tactic 변형]
그냥 gold tactic을 외우지 않기 위해서 다양한 
gold tactic으로 변형해볼 수 있지 않을까? 무슨 말이냐면, 
원래는 apply L 인 gold tactic을 
apply with 이나 eapply 로 치환할 수 있을거 아니야?
이렇게 하면 같은 lemma set으로 다양하게 조립하는 방법을 배울 수 있을거고. 
rewrite도, 그냥 rewrite H를
rewrite <- H 이렇게 바꾸거가나 혹은 rewrite -> H 으로 바꿀 수 도 있을거 아니야.

이렇게 해서 원래는 
(프롬프트 -> gold tactic 1)
이렇게 했던 것을 
(프름프트 -> tactic 1)
(프롬프트 -> tactic 2 equivalent to tactic 1)
(프롬프트 -> tactic 3 equivalent to tactic 1)
...
이런식으로 apply, eapply, rewrite 에 대해서는 다양한 equiavlent한 애를 생성해서 
학습하면 더 다양한 패턴을 소화할 수 있지 않을까.
물론 얘내가 연속으로 있으면 학습이 힘들 수 있으니까 생성하고 랜덤하게 섞어야 겠네.
이걸 근데 llm이 막 만들어주는건 그러니까 판별 트리를 이용해서 뭔가 뚜렷한 규칙을 가지게 
만들고 싶은데 아이디어가 있을까?

(물론, 익명화 기준이다.

case B> 
정답은 있는데 적용을 못한다. 예를 들면, 
apply with 변수를 잘못 적용한다던가. 
아마 이 경우에 대해서는 error message를 만들겠지?

이거 다 끝나고 dpo를 적용해볼까 싶었는데 안된다고 하네.
중간 중간 60000 steps를 돌다가 5000 step 번째마다
dpo를 하면 좋을까? 설계는 어떻게 하고? 

=> error message는 어떻게 다뤄야 할까?
[error message with previous tactic]
이렇게 하고, (previosu tactic, error message)를
거기에 넣은 다음에 맞추게 해야 하나?

[5. 요구 사항]
- 실험하기 이전에 빡세게 동적 디버깅, assert 구문을 넣어서 에러가 없는지 봐줘야 한다.
    - 특히 익명화 규칙이 문제 없이 잘 되어 있는지, (gold랑 프롬프트 익명화 규칙 일정하게)
- 실험하는 중간 중간 모니터링을 해야한다. 메모리가 터지지는 않았는지 등등.
