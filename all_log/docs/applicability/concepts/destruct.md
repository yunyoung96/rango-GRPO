# `destruct` 는 왜 어려운가 — 이름이 아니라 **항**을 골라야 한다

> 다른 채널은 "어느 lemma 인가" 만 맞히면 된다.
> `destruct` 는 **"어느 lemma 를 어떤 인자에 적용하는가"** 다. 공간이 다르다.

---

## 1. 실측 — CompCert rand200 의 destruct 계열 329스텝

```
   ① 단일 이름       153  46.5%  ████████████████████████
   ④ lemma + 인자    144  43.8%  ██████████████████████
   ⑥ 기타             27   8.2%  ████
   ⑤ 괄호 기타         5   1.5%  ▌
   ② if 식             0   0.0%
   ③ match 식          0   0.0%
```

```coq
①  destruct l              destruct H            ← 지역 이름. 검색 문제가 아니다
④  destruct (zle (fst i) x)                      ← ★ 여기가 문제
    destruct (zlt x (snd i))
    destruct (Req_EM_T r (IZR (Zfloor r)))
    destruct (PregEq.eq r' (preg_of r))
    destruct (zle Int64.min_signed s && zle s Int64.max_signed)
⑥  destruct Archi.ptr64 eqn:SF
    destruct (Zle_not_lt with (2 := T emin))      ← with 절까지 붙는다
```

### `if` 가 0% 인 게 뜻하는 것

**조건식이 없는 게 아니라, 조건식이 `destruct` 대상으로 이미 옮겨져 있다.**

```coq
   if zle a b then X else Y          ← 정의 안의 조건
   destruct (zle a b)                ← 증명에서는 이렇게 가른다
      └── 같은 것이다
```

CompCert 은 조건을 **sumbool 을 반환하는 판정 함수**로 쓴다.

```coq
   zle : forall x y : Z, {x <= y} + {x > y}
   peq : forall x y : positive, {x = y} + {x <> y}
   eq_block : forall b1 b2, {b1 = b2} + {b1 <> b2}
```

그래서 "조건 조합이 많다" 는 직관이 맞다 — 다만 그 조합은
**판정 함수 + 인자 선택**의 형태로 나타난다.

### 실제로 쓰이는 머리 (빈도순)

```
   eq_block 19 · zlt 15 · peq 10 · zle 7 · zeq 4 · Req_EM_T 3
   ident_eq 3 · Genv.find_symbol 3 · Rle_or_lt 3 · Int64.eq 2 · IS.mem 2 …
```

**꼬리가 길다.** 상위 5개가 절반쯤이고 나머지는 하나씩이다.

## 2. 공간이 왜 폭발하나

`zle` 는 인자를 2개 받는다. goal 의 닫힌 부분항이 20개면:

```
   이름만 고른다        판정 후보          91개
   항까지 고른다        91 × 20 × 20  ≈  36,400개
                            ▲    ▲
                          인자1  인자2

   3인자 판정이면       91 × 20³      ≈  728,000
```

```
   ┌──────────────────────────────────────────────────┐
   │   항 공간  (수만 ~ 수십만)                         │
   │   ┌──────────────────────────────┐               │
   │   │  이름 공간  91개              │               │
   │   │   zle · zlt · peq · eq_block │               │
   │   └──────────────────────────────┘               │
   └──────────────────────────────────────────────────┘
         ▲ 우리가 다루는 것        ▲ gold 이 사는 곳
```

`apply`·`rewrite` 는 이 문제가 없다 — **인자를 단일화가 채워 준다.**
`apply PTree.gso` 라고만 쓰면 `?i ?j ?x ?m` 이 goal 에서 결정된다.
`destruct` 는 **인자가 결론에 안 나타나므로** 단일화가 못 채운다.

```
   apply  L        L 의 결론 ≟ goal      →  인자가 결정된다
   destruct (L a b) L 을 a b 에 적용     →  a·b 를 **사람이 고른다**
```

## 3. 우리가 어떻게 피하나 — 이름만 준다

```
   프롬프트에 넣는 것:   zle
   모델이 만들어야 하는 것:  destruct (zle (fst i) x)
```

**의도적인 우회다.** 91개를 랭킹하는 문제로 줄이고, 인자 조합은 모델에 맡긴다.
모델은 goal 을 보고 있으므로 `(fst i)`·`x` 를 고르는 건 국소적 판단이다.

### 대가 — 우리 66.0% 는 **이름 기준**이다

```
   @10 66.0%   =  "gold 의 **머리 이름**이 상위 10 안에 있다"
               ≠  "destruct (zle (fst i) x) 를 그대로 만들 수 있다"
```

인자를 틀리면 실패한다. 이 부분은 우리 지표가 **측정하지 않는다.**
정직하게 말해 `destruct` 의 실제 성공률은 66.0% 보다 낮을 것이다.

## 3.5 ★ 실제로 gold 은 어느 채널에서 나오나 — 실측

이건 설계가 아니라 **측정 결과**다. `destruct` 50지점의 gold 을 채널별로 추적했다.

```
   uf (unfold 채널)   36  72%   ██████████████████████████████████
   dc (decide 채널)   10  20%   █████████
   in (apply…in)       4   8%   ███▌
   ap (apply)          1   2%   ▌
   ds (destruct 채널)  0   0%                    ← 하나도 없다
   ✗ 못 찾음          11  22%
```

**`destruct` 의 정답은 대부분 `unfold` 채널이 찾는다.**

```coq
   goal :  … if peq r1 r2 then … else …      ← peq 가 goal 에 이미 있다
   gold :  destruct (peq r1 r2)
                     └── uf 채널이 "goal 에 있는 투명 상수" 로 이미 수집했다
```

CompCert 은 조건을 정의 안에 `if zle a b then …` 으로 써 둔다.
증명에서 그걸 가르려면 **goal 에 이미 보이는 그 함수**를 destruct 하면 된다.
그래서 매칭이 필요 없다 — [unfold.md](unfold.md) 의 열거로 잡힌다.

실제 gold: `zle` · `peq` · `PregEq.eq` · `PTree.elt_eq` · `xorl_match` — 전부 `uf` 에서 나왔다.

### `ds` 채널은 죽어 있다

`destruct_cands` 는 **귀납형 타입 이름**을 낸다:

```
   Z 205 · option 117 · positive 110 · list 103 · bool 102 · val 90 · prod 52 …
```

그런데 gold 은 **함수 이름**이다 (`zle`, `peq`). `destruct Z` 는 뜻이 없다.
**315지점 전체에서 `ds` 가 gold 을 포함한 적이 0회다.**

### `dc` 채널은 단독 기여가 0이다

| 채널 | gold 포함 | **단독 기여** | 후보 중앙 |
|---|---|---|---|
| ap | 115 | 46 | 334 |
| in | 70 | 9 | 618 |
| rw | 88 | 47 | 418 |
| **uf** | 109 | **75** | **7** |
| **ds** | 0 | **0** | 3 |
| **dc** | 36 | **0** | 171 |

> 단독 기여 = 그 채널을 빼면 gold 을 아예 못 찾게 되는 지점 수.

`dc` 가 찾는 36개는 **전부 다른 채널(주로 `uf`)도 찾는다.** 그러면서
후보를 중앙 **171개** 늘린다. 순수 잡음이다.

```
   uf :   후보  7개 →  단독 기여 75    ★ 효율 10.7
   dc :   후보 171개 →  단독 기여  0    ✗ 비용만
   in :   후보 618개 →  단독 기여  9      효율 0.015
```

**`ds`·`dc` 를 빼면 잃는 것이 없고 지점당 잡음 174개가 사라진다.**

## 4. 채널이 어떻게 후보를 찾나

`zle` 는 **goal 에 안 나타난다.** goal 에 있는 건 `Z.le` 다.

```
   goal :  … Z.le (fst i) x …
                ▲
   필요한 연결:  "Z.le 를 판정하는 함수"
                ▼
   zle : forall x y, {x <= y} + {x > y}
                        └── 결론 안에 Z.le 가 있다
```

`decide_cands` 가 하는 일:

```
   후보 c 마다
     ① 결론까지 Π 를 벗긴다
     ② 결론의 머리가 귀납형인가            (sumbool·or·and·exists·spec 류)
     ③ 결론의 **인자 중 하나**가 goal 의 닫힌 부분항과 실제로 단일화되나
```

**③ 이 핵심이다.** 처음엔 "머리만 겹치면 통과" 로 느슨하게 뒀더니:

```
   느슨:  후보 107 → 490    destruct @10  52% → 46%   ← 오히려 나빠졌다
   조임:  후보        91    destruct @10  회복
```

후보가 늘면 신호가 못 가른다. **필터를 넓히는 게 항상 이득이 아니다.**

> 그런데 §3.5 의 실측은 더 나아간다 — 조인 뒤에도 `dc` 의 **단독 기여는 0** 이다.
> 조이는 것으로 부족하고, 이 채널은 **빼는 게 맞다.**

### 왜 `sumbool` 만 보면 안 되나

```coq
   prog_defmap_linkorder : … -> exists gd2, …        ← 결론이 exists
   Pos.compare_spec      : CompareSpecT … …          ← 3분기 귀납형
```

`destruct (L a b)` 의 `L` 은 결론이 **어떤 귀납형이든** 된다.
`sumbool`/`bool` 로 좁혔더니 위 둘을 놓쳤다.

## 5. 그래서 78.0% 에서 막혀 있다

```
   필터 회수율 (r10 · 450지점)

   unfold    100.0%  ██████████████████████████████████████████████████
   apply      95.8%  ███████████████████████████████████████████████▌
   rewrite    94.7%  ███████████████████████████████████████████████
   destruct   78.0%  ███████████████████████████████████████    ← 여기
```

전체 92.3% 를 끌어내리는 **유일한 원인**이다.

### 못 찾는 22% 는 뭔가

| 유형 | 왜 못 찾나 |
|---|---|
| 인자가 goal 에 **없는** 판정 | `destruct (zle 0 (align x y))` — `align x y` 를 먼저 만들어야 한다 |
| `&&` 로 **합성**된 조건 | `destruct (zle a s && zle s b)` — 판정 둘의 부울 결합 |
| `eqn:` 붙은 상수 destruct | `destruct Archi.ptr64 eqn:SF` — 상수를 가르는 것 |
| `with` 절이 붙은 것 | `destruct (Zle_not_lt with (2 := T emin))` |

앞의 둘은 **항 합성**이 필요하다. 이름 검색으로는 원리적으로 못 닿는다.

## 6. 정리 — 다른 채널과 뭐가 다른가

| | 고를 것 | 인자를 누가 채우나 | 공간 |
|---|---|---|---|
| `apply` | 이름 | **단일화** | 이름 수 |
| `rewrite` | 이름 (+좌/우변) | **단일화** | 이름 × 2 |
| `unfold` | 이름 | 없음 | 3~7개 |
| **`destruct`** | **이름 + 인자** | **사람/모델** | 이름 × 부분항^인자수 |

```
   다른 채널:  검색 문제         "어느 lemma 인가"
   destruct :  검색 + 합성 문제  "어느 lemma 를 무엇에"
                     └── 우리는 앞쪽만 푼다
```

앞으로 할 수 있는 것은 [../future-work/](../future-work/README.md) 에 있다 —
후보를 **이름이 아니라 적용된 항으로** 내려면 인자 후보를 goal 부분항으로
제한하고 타입으로 걸러야 한다. 91 × 20² 은 다 검증하기엔 크지만
**타입이 맞는 조합만**이면 훨씬 작다.
