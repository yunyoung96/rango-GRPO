# 학습에도 이 검색을 쓸 수 있나

> 결론부터: **추론은 막힘없다. 학습이 제약이다.**
> 그리고 목적이 "문법별로 premise 를 다르게 준다" 라면 학습이 **필수**가 된다.

---

## 1. 왜 문제가 되나

필터는 **살아있는 Coq 환경**을 훑는다. 그래서 그 파일의 의존성이 컴파일(`.vo`)돼 있어야 한다.

| | 저장소 | 컴파일 | 필터 사용 |
|---|---|---|---|
| TEST | 12개 | ✅ | 가능 |
| VAL | 6개 | ✅ | 가능 |
| CUTOFF | 2개 | ✅ | 가능 |
| **TRAIN** | 2,270개 | ❌ | **불가** |

TRAIN 은 GitHub 수집본이고 `.vo` 가 없다.

---

## 2. 추론은 막힘없다 — 확인함

`ProofManager` 가 증명 탐색 내내 Coq 세션을 들고 있다
(`src/model_deployment/proof_manager.py`). 플러그인은 거기서 그냥 돈다.

그래서 `coq_search_pool` 을 **주입식**으로 설계해뒀다:

```
탐색기가 goal 마다 질의 → coq_search_pool.put(key, names)
lm_example 이 풀을 만들 때 → coq_search_pool.extra(key) 로 꺼내 합침
세션이 없으면(학습·오프라인) 조용히 빈 목록 → 동작이 안 바뀐다
```

## 4. ★ 해본 것 — 의존성 조사

**필터를 TRAIN 에 쓰려면 빌드가 필요하고, 빌드의 난이도는 의존성이 정한다.**
그래서 TRAIN 이 무엇을 참조하는지 쟀다.

```
sentences.db 의 file_path 를 라이브러리별로 집계
```

| | 문장 수 |
|---|---|
| 프로젝트 파일 | 541,835 |
| 라이브러리 | 40,202 |
| └ `coq/theories` (**stdlib**) | 40,202 |
| └ mathcomp · stdpp · ext-lib … | **0** |

**참조하는 외부 라이브러리가 stdlib 하나뿐이다.** 프로젝트 2,270개 전부.

> 주의: `Require` 문 자체는 db 에 없다(선언문만 저장). 위는 **참조된 선언의 출처 경로**로
> 센 것이다. 실제로 `Require` 는 했지만 그 파일의 선언을 안 쓴 라이브러리는 안 잡힌다.
> 그래도 "무거운 외부 라이브러리를 실질적으로 쓰지 않는다" 는 신호로는 충분하다.

### 그래서 빌드가 현실적이 된다

```
기존 opam switch (Coq 8.18) 그대로 쓸 수 있다
→ "opam 버전 변경 금지" 제약을 안 어긴다
```

**소스 복구도 이미 검증됐다** — `splits/commits.json` 이 `owner/repo → 커밋 해시` 를
2,955개 담고 있고, 예전에 2,268/2,270 프로젝트 · 18,531/18,911 파일(98.0%)을 복구했다.
`superwalter/French-thesis` 를 핀된 커밋으로 체크아웃하니 **줄 번호까지 db 와 일치**했다.

코드: `scripts/recover_train_repos.py`

## 5. ★ 해본 것 — 분포 불일치의 실효성

"학습은 현행, 추론만 새 검색" 이 안전한가를 **직접 쟀다.**
같은 487 스텝(CompCert rand200 · gold prefix 오라클 · ckpt-32000):

| | top1 | top8 | 도달성 실패 |
|---|---|---|---|
| 20000 현행 검색 | 19.9% | 34.5% | 49.3% |
| 32000 현행 검색 | 20.5% | **39.2%** | 45.4% |
| 32000 + **필터 풀 주입** | 21.4% | **37.0%** ↓ | 48.5% ↑ |
| 32000 + gold 강제 주입 | 23.2% | **43.5%** | 38.8% |

**필터 풀을 붙였더니 오히려 −2.2pp.**

원인은 분포 불일치가 아니라 **배분**이었다. 다섯 채널을 합쳐 tf-idf 로 정렬했고,
그게 계산상 최악이다:

| 배분 | E[gold 프롬프트에 실림] |
|---|---|
| 합쳐서 상위K (이번에 쓴 것) | **58.0%** |
| 물채우기 | **69.5%** |

`unfold` 채널(지점당 4~7개)이 수백 개짜리 채널에 묻혀 **슬롯 0칸**을 받는다.

### 그리고 v9 가 이미 경고했다

`ckpt-47000` 로 같은 gold 주입 실험을 했을 때:

| | Δ | p |
|---|---|---|
| 원래 프롬프트에 있었음 (n=204) | +1.0pp | 0.880 |
| **진짜 새로 넣어줌 (n=113)** | **+0.9pp** | **1.000** |

**프롬프트에 넣기만 해서는 안 된다.** 상위 순위여야 한다.
같은 실험에서 **이름을 직접 써 주면 조립 성공 72.7%** 였다 — 간극은 "있다" 와 "고른다" 사이다.

## 7. 목적이 "문법별 premise" 라면 (B) 가 안 된다

지금까지 (B) 를 권한 전제는 **프롬프트 형식이 안 바뀐다** 였다. 그런데 목적이
문법별로 다른 premise 를 주는 것이라면 형식이 바뀐다:

```
지금                        원하는 것
[PREMISES]                  [APPLY]    Lemma foo : …
Lemma foo : …               [REWRITE]  Lemma bar : …
Lemma bar : …               [UNFOLD]   Definition baz := …
                            [DESTRUCT] …
```

**형식이 바뀌면 모델이 그걸 읽는 법을 배워야 한다.** 추론에서만 넣으면
학습 때 본 적 없는 토큰이 들어가고 구획의 의미도 모른다.

그러면 순서가 이렇게 된다:

```
① TRAIN 소스 복구      splits/commits.json — 검증됨 (98.0%)
② TRAIN 빌드            의존성이 stdlib 뿐 — 기존 switch 로 가능
③ TRAIN 에 필터 적용    ← 진짜 병목
④ 구획 프롬프트로 재학습
```

### ③의 비용

스텝 249만 × 지점당 0.3~0.5s = 코어 하나로 **20,000시간**. 다만:

- **파일당 색인을 한 번 만들고 재사용**한다 (색인 0.8s + 스텝당 0.3s).
  파일 하나에 180스텝이면 스텝당 실효 비용은 0.3s 근처.
- **전부 할 필요가 없다.** 구획 프롬프트를 배우는 데는 10~20만 스텝이면 충분할 수 있다.
- 파일 단위로 **병렬화가 자명**하다.

## 8.5 ★ 표본 빌드 실측 (2026-08-30, 표본 20 프로젝트)

`scripts/train_build_probe.py` — `git init` + `git fetch --depth 1 origin <sha>`
+ `git checkout FETCH_HEAD` 로 복구하고 `coq_makefile`/`make` 로 빌드했다.

```
■ db 프로젝트 2,270 · 커밋 매칭 2,268
```

| 결과 | 개수 | 비율 |
|---|---|---|
| 완전 빌드 ✓ | 6 | 30.0% |
| 부분 빌드 | 5 | 25.0% |
| 소량만 | 5 | 25.0% |
| 클론 실패(timeout) | 2 | 10.0% |
| 빌드 0 | 2 | 10.0% |
| **쓸 만한 것 (완전+부분)** | **11** | **55.0%** |

**그런데 파일 기준 컴파일률은 427/9,380 = 4.6% 다.**

```
   프로젝트 기준 55%          파일 기준 4.6%
   ───────────────────    ─────────────────────
   ✓✓✓✓✓✓ 부분×5           대형 프로젝트가 대부분 실패
   작은 프로젝트가            HoTT      1/560
   잘 빌드된다               undecid  51/673
                            CompCert 52/253
```

**작은 프로젝트는 통째로 빌드되고, 큰 프로젝트는 앞부분만 된다.**
데이터포인트는 큰 프로젝트에 몰려 있으므로 **4.6% 쪽이 정직한 수치**다.

### ★★ 정정 — 이 4.6% 는 데이터가 아니라 **우리 하네스**를 잰 값이다

프로브가 실패 사유로 `make: *** Error 2` 같은 **꼬리 160자만** 남겨서
실제 Coq 오류를 못 봤다. 다시 재보니 원인이 전혀 달랐다.

`scripts/train_build_why.py` — make 꼬리가 아니라 **첫 Coq 오류**를 잡는다 (표본 12):

```
   4  하네스: 논리경로 매핑 불일치
   3  클론 실패 (timeout)
   3  오류 없음/미상
   1  makefile 실패
   1  완전 빌드
   ───────────────────────────
   0  버전 드리프트로 분류된 것
```

**`_CoqProject` 가 원래 있던 프로젝트는 12개 중 2개뿐이다.**
나머지 10개는 우리가 이렇게 지어냈다:

```bash
find . -name '*.v' > _f && { echo '-R . Top'; cat _f; } > _CoqProject
```

그리고 그게 실패 원인이 된다. 표본 하나를 직접 열어 확인했다:

```
Error: Invalid character '-' in identifier "pierce-lem".
```

파일이 `coq/pierce-lem.v` 인데 `-R . Top` 이 모듈 이름을 `Top.coq.pierce-lem` 으로
만든다. **하이픈은 Coq 식별자에 못 쓴다.** 저장소 잘못도, Coq 버전 잘못도 아니다.

같은 프로젝트의 다른 오류는 이랬다:

```coq
  destruct (H {u : unit | p} (fun _ => False) p) as [G _].
  cut                     ← 인자가 비어 있다
  apply G.
```

```
File "./coq/frobenius2.v", line 17: Error: Illegal tactic application: got 1 extra argument.
```

**저장소에 미완성 파일이 커밋돼 있다.** 어떤 Coq 버전에서도 안 된다.

그리고 `AbsInt-CompCert 52/253` — CompCert 은 `CoqStoq/test-repos/compcert` 에서
**우리가 이미 완전히 빌드해 쓰고 있다.** 프로브가 실패한 건 `./configure` 없이
generic `-R . Top` 으로 때린 탓이다. 역시 하네스다.

### 그래서 (A) 의 판정은 **미정**이다

| | |
|---|---|
| 소스 복구 | ✅ 2,268/2,270 = **98.0%** |
| 의존성 | ✅ 2,270 프로젝트가 **stdlib 만** 참조 (mathcomp·stdpp·ext-lib 0) |
| 빌드 | ❓ **아직 제대로 안 재봤다.** 4.6% 는 하네스 값이다 |

**다음에 할 것 — 빌드 하네스를 고치고 다시 잰다:**

1. 저장소의 **자기 `_CoqProject`/`Makefile`/`./configure`** 를 먼저 쓴다.
   없을 때만 만들고, 그때도 `-R . Top` 대신 `-Q <dir> <합법식별자>` 로 만든다.
2. 파일명에 하이픈·공백이 있으면 논리경로에서 걸러 낸다.
3. 클론 timeout 을 늘리고 재시도한다 (표본의 25%가 여기서 죽었다).
4. 그러고도 안 되는 것만 **진짜 버전 드리프트**로 센다.
