# [B. sft] 설계 답변 (2026-09-02 · retrieval r19/랭커 r18 실측 근거 포함)

────────────────────────────────────────────────────────
[1. 프롬프트 구성] 에 대한 답
────────────────────────────────────────────────────────

■ 지역 가설 익명화 — **하지 말 것을 추천**

  근거 3개:
  ① 지역 이름(H, H0, IHn)은 상태마다 다시 태어나는 이름이라 "암기" 위험이
     없다 — 전역 lemma 암기와 문제 구조가 다르다. 모델이 하는 일은 암기가
     아니라 **화면에 보이는 이름의 참조**다.
  ② gold 의 절대다수가 지역 가설을 인자로 쓴다(destruct H, rewrite IH…).
     익명화하면 상태 표시 ↔ tactic 출력의 대응을 한 겹 더 배워야 해서
     난이도만 오른다.
  ③ IHn(귀납가설)·Heq 같은 관용 이름은 그 자체가 의미 신호다.
  단, 일관성 하나만 강제: 프롬프트 상태 표시에 쓰인 이름 그대로 tactic 이
  참조하게 한다 (익명화 없음 = 자동으로 성립).
  전역 lemma 익명화는 계획대로 진행하되 stdlib 제외 ✓ — 이전 실측(Ltac
  회상 61.5% 익명화O vs notation 53.5% 익명화X)도 전역 이름에 한한 결론.

■ 섹션당 10개 vs 20개 — **비대칭 추천: ap/in/rw/Others = 10 · rwh 만 20**

  r19 자기채널 실측(@10 → @20 이득):
      apply       87 → 92   (+5)
      apply-in    63 → 71   (+8)
      rewrite     77 → 82   (+5)
      rewrite-in  53 → 68   (+15)  ← 여기만 이득이 압도적
  토큰 비용: premise 1개 ≈ 25~40tok → 블록 +10개 ≈ +300~400tok.
  전 블록 20개면 +1.2~1.6k tok 로 [PROOFS]/[STATE] 예산을 잠식한다.
  rwh 만 20개로 하면 +0.4k 로 rwh 의 +15pp 를 산다. (원하면 전블록 10 vs
  비대칭 A/B 한 번으로 확정 — 측정 인프라는 이미 있음)

■ 블록 안 순서 = 랭킹순 유지 (순위 자체가 신호다. 셔플 금지)

[2. sft 학습 프레임워크] 에 대한 답
────────────────────────────────────────────────────────

■ case A (정답이 프롬프트에 있음) — 설계 그대로 승인. 주의 2개:
  ① 다중 gold(rewrite A, B)는 **전부** 있어야 case A — 우리 표의 All 열이
     그 판정 기준이다 (Any/All 인프라 재사용).
  ② "있음" 판정은 익명화 후 이름 기준(동일 익명화 맵 통과 후 비교).

■ case B (없음 → 주입) — 골격 승인 + 설계 디테일 3개:
  ① 제거 대상은 **블록의 하위권에서** 뽑아라 (상위 제거는 프롬프트 분포를
     배포 분포에서 멀어지게 한다).
  ② 주입 위치는 **균등 랜덤** — 고정 위치(꼴찌 등)는 위치=정답 신호로 새어
     "위치만 보는" 모델을 만든다.
  ③ 채널 정확성(지적한 그대로): FORM_CH 매핑을 단일 소스로 —
        apply/eapply/exact/eexact → [PremisesForApply]   (r17 에서 exact 편입)
        apply … in → [PremisesForApplyIn]
        rewrite → [PremisesForRewrite] · rewrite … in → [PremisesForRewriteIn]
        그 외 형태 → [Others]
     구현은 수집기·랭커가 쓰는 FORM_CH 를 import 해서 쓰고, 별도 매핑을
     복제하지 말 것(어긋나면 조용히 오염 — 우리가 이미 당해 본 부류).
  ④ 주입 premise 의 본문은 실제 선언문(선언 DB)으로 — 형식이 다른 항목은
     그 자체가 "이게 정답" 신호가 된다.

────────────────────────────────────────────────────────
[3. gold tactic 변형] — "판별트리 기반 뚜렷한 규칙" 제안
────────────────────────────────────────────────────────

핵심 아이디어: **변형은 문법 규칙표로 만들고, 채택은 커널이 판정한다.**
LLM 생성 없이 결정적으로:

  1단 · 변형 후보 생성 (순수 구문 규칙, 채널별):
     apply L      ⇒ eapply L                        (항상 후보)
     eapply L     ⇒ apply L                         (탈-evar 가능할 때만)
     apply L      ⇒ apply L with (x := t)           (2단 검증이 t 를 줌)
     apply L      ⇒ exact (L t₁ … tₙ)               (완전 적용꼴)
     rewrite H    ⇒ rewrite -> H · erewrite H
     rewrite H    ⇒ rewrite <- H′                   (등식 방향 반전)
     rewrite H    ⇒ rewrite H at n / in ⋆           (출현 지정)

  2단 · 커널 채택 판정 (r19 의 probe_ok 재사용 — 후보당 ~0.11ms):
     변형 t′ 를 assert_succeeds 로 실행해 보고,
     **동치 인증 = 실행 후 상태의 판별트리 라벨열(preorder_of) 해시가
     원본 gold 실행 후와 일치** 하는 것만 채택.
     → "판별트리를 이용한 뚜렷한 규칙"의 정확한 형태: 동치성의 정의 자체를
       트리 라벨열 일치로 둔다. (evar 이름 차이는 라벨 `*` 로 흡수됨)
     부산물: eapply→apply with 의 인스턴스 t 는 검증 과정의 evar 해에서
     그대로 받아온다 (별도 탐색 불필요).

  3단 · 배치: 지점당 변형 ≤3(원본 포함), 생성 후 **지점 단위 전역 셔플**
     (같은 지점의 변형이 이웃 배치되면 대조 암기가 일어난다).

────────────────────────────────────────────────────────
[4. 틀린 답 페널티 · DPO · error message] 에 대한 답
────────────────────────────────────────────────────────

■ 우선순위 0: case A(미검색 lemma 사용)는 페널티 이전에 **구조로 차단** —
  생성 시 제약 디코딩: 프롬프트에 등장한 익명 이름 집합(_L0…)+지역 가설만
  lemma 자리 토큰으로 허용. 페널티로 배우게 하는 것보다 싸고 확실하다.
  (학습으로도 막고 싶으면 아래 DPO 부정례에 포함)

■ DPO 삽입 설계 — "60k 중 5k 마다" 질문에 대한 구체안:

     SFT 5,000 step → DPO 500~1,000 step → SFT … 반복 (비율 ~10:1)
     · reference 모델 = 직전 SFT 스냅샷으로 매 라운드 갱신
       (처음 스냅샷 고정은 후반에 ref 와 정책이 멀어져 신호가 죽는다)
     · DPO 는 LR 을 SFT 의 1/5~1/10, β 0.1~0.3 시작
     · 끝에 몰아서 하는 DPO 는 지적대로 부적합 — 분포가 이미 굳는다

  부정례(rejected) 채굴 두 갈래:
     (a) rollout: 5k 라운드마다 현재 모델로 프롬프트당 k=4 샘플 →
         실패한 출력(검증기는 이미 있음: coqtop 실행)을 rejected 로
     (b) **랭킹-이웃 하드네거티브**(판별트리 근거): gold 와 같은 블록의
         상위 비정답 lemma 로 치환한 tactic — 우리 랭커가 헷갈리는 딱 그
         후보라 정보량 최대. 채택 전 probe_ok 로 "정말 실패함"을 확인해
         가짜 부정례(사실은 되는 수)를 걸러낸다.
     쌍 = (prompt, chosen=gold, rejected=위 중 하나), 라운드당 쌍 수는
     SFT 표본의 ~10% 로 시작.

■ error message 섹션 설계:

     [ErrorFeedback]
     none                            ← 평시 SFT (섹션 헤더는 항상 존재)

     [ErrorFeedback]
     prev: apply lt_le_trans.
     error: Unable to unify "?y < ?z" with …    ← 재시도 학습/추론 시

  헤더를 항상 두는 이유: 추론 루프에서 에러 후 재시도할 때 같은 형식에
  내용만 채우면 되고, 학습·추론 간 형식 스위치가 없어야 한다. <empty>
  같은 인공 토큰보다 `none` 한 단어가 낫다(자연어 사전확률 활용).
  데이터: 탐색 루프 로그에서 (상태, 실패 tactic, error, 이후 성공 tactic)
  을 수집해 2차 SFT — 이것만으로도 "에러를 읽고 고치는" 행동이 생긴다.
