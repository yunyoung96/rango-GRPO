# checkpoint-25000 실험 — 검색이 문제인가, 조립이 문제인가

> 대상: `models/rango-qwen3b-v9-ft/checkpoint-25000` (25,000/60,000 스텝 = 42%, loss 0.452)
> 데이터: CompCert rand200 (held-out) · `apply`/`eapply`/`rewrite`/`erewrite` 스텝

---

## 0. 세 줄 요약

1. **검색은 66.2% 성공**한다 — gold lemma 가 프롬프트에 실려 있는 비율.
2. **그런데 실려 있어도 37.9%는 못 고른다.** 맨 앞에 강제로 꽂아 줘도 **+4.9pp** 뿐이다.
3. **이름만 정해 주면 조립은 70.7% 로 잘 한다** — 자연 상태(31.4%)의 **2.3배**.
4. 분해하면 더 뚜렷하다 — **조건부 조립은 66~70% 로 일정**하고(A 66.2% · B 65.7% · C 69.7%)
   움직이는 것은 **선택**뿐이다(A 43.8% → B 55.2%).
   → 병목은 "조립"이 아니라 **"고르기"** 다.
5. 그 원인 후보: **학습 분포**. `Module.member` 형태가 TRAIN 스텝의 **0.8%**,
   CompCert 스텝의 **12.2%** 다(**15배**). 모델은 그 형태를 거의 배운 적이 없다.

## 1. "이름을 써 준다"가 무슨 뜻인가 — Arm C 의 정확한 정의

프롬프트 끝에 **`<head> <lemma>` 까지만** 이어 붙이고, 모델에게 **그 뒤를 잇게** 한다.

```
프롬프트 … [TACTIC]
                    ← 여기까지가 평소
프롬프트 … [TACTIC] rewrite Pregmap.gso
                                        ← 여기까지 써 주고, 이 뒤를 생성시킨다
```

**`apply <lemma>` 뒤에는 아무것도 안 올 수도 있고, 많이 올 수도 있다.**
gold 기준 그 꼬리의 분포(382스텝):

| 이어지는 것 | 비중 | 예 |
|---|---|---|
| `.` 만 (거기서 끝) | **48.6%** | `apply bpow_gt_0.` |
| `; <tactic>` (연쇄) | **28.2%** | `eapply agree_regs_incr; eauto.` |
| `with (x := e)` | 7.5% | `apply Rle_trans with x.` |
| `in H` | 7.3% | `apply L in H0.` |
| `by <tactic>` | 4.2% | `rewrite BofZ_plus by auto.` |
| `, <다음 rewrite>` | 3.4% | `apply f_equal, eqbool_irrelevance.` |

즉 **절반은 이름이 곧 끝**이지만, 나머지 절반은 연쇄·인자·방향·부수goal 처리를
더 붙여야 한다. Arm C 는 그 나머지를 모델이 만들어 내는지를 본다.

### 실제 성공 사례

```
써 준 것                             모델이 이어붙인 것
rewrite Pregmap.gso              →   ; auto.          ★
eapply agree_regs_incr           →   ; eauto.
eapply match_stacks_invariant    →   ; eauto.
apply Rle_trans                  →   with x.
apply f_equal                    →   , eqbool_irrelevance.
apply bpow_gt_0                  →   .
rewrite sub_zero_l               →   .
```

★ 첫 줄이 `functor-names.md` 에서 분석한 바로 그 스텝이다.
자연 상태에서는 **94회 시도 · 58종**을 뱉고도 `gso` 를 한 번도 못 냈는데,
이름을 써 주니 `; auto.` 를 붙여 **gold 와 정확히 일치**시켰다.

## 2. 실험 설계 — 네 지표

`scripts/oracle_lemma_eval.py`. gold 의 k번째 지점을 **그대로 오라클로 주고**(prefix)
다음 한 수를 물어본다. 후보 8개, 재시도 없음.

| | 조작 | 답하는 질문 |
|---|---|---|
| **[검색]** | 조작 없음. gold lemma 이름이 프롬프트에 **실려 있는지만** 본다 | 검색이 실어 주긴 하나 |
| **A 자연** | 평소대로 생성 | 기준선 |
| **B 오라클 검색** | gold lemma 의 **선언문을 `[PREMISES]` 맨 앞에 꽂고** 생성 | **검색이 완벽하면 되는가** |
| **C 오라클 이름** | `<head> <lemma>` 까지 써 주고 나머지만 생성 | **순수 조립 능력** |

성공 기준은 **gold 와 문자열 일치**다(Coq 을 안 돌린다). 따라서 전부 **하한**이다 —
`eapply L` 이 gold `apply L` 과 다르면 Coq 에서 통해도 실패로 센다.

### B 의 함정 하나 — 조회 품질

gold lemma 의 선언문을 이름으로 찾아야 하는데, `gso` 는 PTree·PMap·IMap·EMap·ITree 에
**전부** 있다(맨 이름 모호성, `functor-names.md` §9). 엉뚱한 명제를 꽂으면 실험이 무효다.
→ 세 단계로 좁히고 품질을 기록한다: **정확**(한정자가 module 컬럼에 있음) →
**프로젝트**(같은 compcert 파일) → **모호**(아무거나).

## 3. 결과 (382스텝)

```
                 스텝   [검색]실림  선언없음 │  A 이름/일치  │  B 이름/일치  │  C 조립
   전체           382     66.2%     17.0%  │ 45.8% / 31.4% │ 55.2% / 36.3% │  70.7%
```

### 3-1. 검색이 실어 줬는가로 가르면

| | 스텝 | A 이름맞힘 | A gold일치 | B gold일치 | **C 조립** |
|---|---|---|---|---|---|
| **프롬프트에 있음** | 253 | **62.1%** | 43.1% | 50.5% | **70.4%** |
| **프롬프트에 없음** | 129 | **14.0%** | 8.5% | 10.6% | **71.3%** |

**검색은 결정적이다** — 실려 있으면 이름맞힘 62.1%, 없으면 14.0% (**4.4배**).

**그런데 두 가지가 이상하다.**

* 실려 있는데도 **37.9%는 못 고른다.**
* 안 실린 129스텝에 **강제로 꽂아 줘도** gold일치가 8.5% → **10.6%** 로 거의 안 움직인다.

★ 그리고 **C 는 실림 여부와 무관하다**(70.4% vs 71.3%).
→ **이름만 정해지면 조립은 똑같이 잘 한다.** 못 하는 건 이름을 고르는 일이다.

### 3-2. 조회 품질별 (B 의 신뢰도)

| 품질 | 스텝 | 실림 | A 이름/일치 | B 이름/일치 |
|---|---|---|---|---|
| **정확** | 54 | 25.9% | 24.1% / 13.0% | **42.6% / 31.5%** |
| 프로젝트 | 205 | 82.4% | 56.6% / 38.5% | 61.0% / 41.0% |
| 모호 | 58 | 36.2% | 17.2% / 10.3% | 46.6% / 24.1% |
| 없음(선언 부재) | 65 | 75.4% | 55.4% / 43.1% | — |

**"정확" 54스텝만 보면 B 가 A 대비 이름맞힘 24.1% → 42.6%, gold일치 13.0% → 31.5% 로
2.4배 오른다.** 이 구간은 실림이 25.9% 로 낮은(=검색이 실패한) 어려운 자리인데,
정확한 명제를 꽂아 주면 크게 오른다.

→ 전체 B 가 +4.9pp 에 그친 것은 **"모호"가 엉뚱한 명제를 꽂아 희석한 탓**일 수 있다.
표본이 작아 단정은 못 한다. **재실험 필요**(§6).

### 3-3. 사다리

| 단계 | gold 일치 |
|---|---|
| 자연 (A) | 31.4% |
| + gold lemma 를 프롬프트 맨 앞에 꽂음 (B) | 36.3% |
| + **이름까지 지정** (C) | **70.7%** |

검색을 완벽하게 만들면 **+4.9pp**, 선택을 완벽하게 만들면 **+39.3pp**.

### 3-4. ★ B 를 "선택"과 "조립"으로 분해 — 못 하는 건 조립이 아니다

"꽂아 줘도 안 된다"를 두 단계로 나눈다.
**선택** = 후보 8개 중 하나라도 그 이름을 언급했는가.
**조립(조건부)** = 언급한 것들 중 gold 와 일치한 비율.

| | n | A 언급 | A 조건부 조립 | B 언급 | B 조건부 조립 | C 조립 |
|---|---|---|---|---|---|---|
| **전체** | 317 | 43.8% | **66.2%** | **55.2%** | **65.7%** | 69.7% |
| 원래 없던 것 | 113 | 15.9% | 61.1% | 29.2% | 36.4% | 72.6% |
| 조회 "정확"만 | 54 | 24.1% | 53.8% | 42.6% | **73.9%** | 79.6% |

**전체 행이 결정적이다.**

* 꽂아 주면 **선택이 43.8% → 55.2% (+11.4pp)** 오른다
* 그런데 **조건부 조립은 66.2% → 65.7% 로 그대로**다
* 그리고 그 값이 **C(69.7%)와 거의 같다**

> **조립 능력은 이름이 정해지면 66~70% 로 일정하다.**
> 병목은 **눈앞에 꽂아 줘도 44.8% 가 그 이름을 안 쓴다**는 것이다.

즉 "retrieval 에 꽂아 줘도 **조립을 못 한다**"가 아니라
"retrieval 에 꽂아 줘도 **여전히 안 고른다**"가 맞다.

예외 하나: **원래 프롬프트에 없던 113스텝**은 B 조건부 조립이 36.4% 로 뚝 떨어진다.
검색이 원래 실패한 자리는 tactic 자체도 어렵다(인자·연쇄가 복잡하다).

## 3-5. 왜 안 고르나 — 학습 분포를 보면

**CompCert 는 학습셋에 없다**(held-out). 그런데 문제는 그것만이 아니다.
`Module.member` 형태의 **한정이름을 tactic 인자로 쓰는 패턴 자체**가 학습에 거의 없다.

| | 스텝에 한정이름 `M.f` 포함 | 그중 펑터 모듈 |
|---|---|---|
| **TRAIN** (600예제 표본) | **0.8%** | ~0% (표본에서 0건) |
| **TEST · CompCert** (113,078스텝) | **12.2%** | **4.0%** |

**15배 차이다.** 학습 표본이 어디서 오는지 보면 이유가 명확하다.

```
표본이 온 프로젝트 상위 (294종 중)
   32 coq-community-corn      26 LASER-UMASS-TacTok
   24 coq-community-gaia      21 UniMath-Schools
   12 HoTT-Coq-HoTT           11 coq-synthetic-incompleteness

   CompCert 계열에서 온 스텝: 2/600 = 0.3%
```

학습은 **corn·gaia·UniMath·HoTT** 같은 수학 라이브러리가 지배한다. 이들은 모듈
시스템을 거의 안 쓰고 평평한 이름공간을 쓴다. CompCert 계열
(`CompCertMod`·`oeuf`·`VeriSparc`)은 전체 2,182 프로젝트 중 몇 개뿐이고
학습 스텝의 **0.3%** 만 기여한다.

(참고: 학습셋 60개 프로젝트를 훑으면 tactic 인자 한정 참조의 25.2% 가 펑터 모듈
소속이라 CompCert(27.0%)와 비슷하다. 그런데 그게 **네 프로젝트에 몰려 있고**
7/11 은 0% 다. 즉 "학습셋에 존재하지만 학습 분포에는 거의 안 나온다.")

**가설**: 44.8% 가 꽂아 줘도 안 쓰는 이유는 "검색을 못 읽어서"가 아니라
**그 형태의 이름을 tactic 인자로 쓰는 패턴을 거의 안 배웠기 때문**이다.

이 가설은 C(69.7%)와도 일관된다 — 이름을 **써 주면** 고르는 결정을 안 해도 되고
꼬리만 이으면 되므로, 안 배운 부분을 우회한다.

**확인 방법**: `Module.member` 참조가 많은 프로젝트만으로 검증 셋을 만들어 next-step 을
재고 CompCert 수치와 비교한다. 그러면 "형태를 안 배웠다"인지 "CompCert 가 어렵다"인지
갈린다. 더 나아가면 학습 샘플링 가중치로 CompCert 계열 비중을 올려 본다
(데이터 재구성 없이 shuffled index 로 가능).

## 5. 해석 — 무엇이 병목인가

두 실험이 같은 곳을 가리킨다.

> **모델은 "무엇을 쓸지"를 모른다. "어떻게 쓸지"는 안다.**

* 도달성 실패 52% vs 조립 실패 14.8% (**3.5배**)
* 이름을 주면 조립 성공 70.7% vs 자연 31.4% (**2.3배**)

그런데 도달성 실패의 **원인이 검색만은 아니다**.

```
도달성 실패 ≈ 52%
  ├─ 검색이 안 실어서        ≈ 34%  (129/382 이 프롬프트에 없음)
  └─ 실렸는데 못 골라서       ≈ 25%  (253 중 37.9%)
```

그리고 **꽂아 줘도 안 쓴다**(B 가 +4.9pp)는 사실이 두 번째 항을 뒷받침한다.
검색을 완벽하게 만들어도 절반쯤만 회수된다는 뜻이다.

★ 그런데 §3-4 의 분해가 이를 더 정확히 만든다 — **못 하는 건 조립이 아니라 선택**이다.
조건부 조립은 A 66.2% · B 65.7% · C 69.7% 로 **일정**하고, 움직이는 것은 선택뿐이다
(A 43.8% → B 55.2%). 그리고 §3-5 는 그 선택 실패의 원인으로 **학습 분포**를 지목한다.

★ 다만 §3-2 의 "정확" 구간(+18.5pp)이 반례일 수 있어, 검색 쪽 결론은 **잠정**이다.

## 6. 그래서 다음

| 표적 | 수단 | 근거 | 상태 |

| 실렸는데 못 고르는 25% | **학습 분포** — `Module.member` 형태가 TRAIN 0.8% vs TEST 12.2% | §3-5 | 미조사 |
| | premise **선택** 능력 — 재랭킹·프롬프트 위치·개수 | 꽂아 줘도 44.8% 가 안 씀 | 미조사 |
| 조립 15% | DPO 형태 쌍 | `../../dpo-design.md` Tier A | 설계만 |
| 탐색 낭비 | `try_candidates` 1 → 8 (Coq 비용 1.00→1.19회) | 시도 하나가 INVALID 하나로 죽는다 | 미착수 |

**재실험이 필요한 것**

1. **B 를 "정확" 조회만으로** 다시 — 모호가 희석했는지 가른다. 펑터 전개를 먼저 하면
   "정확" 비율이 크게 오르므로 그 뒤에 하는 게 낫다.
2. **C 를 Coq 검증으로** — 지금은 gold 문자열 일치라 하한이다. `eapply` vs `apply`
   같은 동치 형태를 세면 70.7% 가 더 오를 것이다.
3. **선택 능력 절제** — premise 개수를 100 → 20 으로 줄이면 어떻게 되나.
   "고를 게 너무 많아서 못 고른다"면 줄이는 쪽이 이긴다.
