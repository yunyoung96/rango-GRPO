# rango-augmented 재학습 결과 총정리

작성 2026-08-05 16:30 KST. 브랜치 `rango-augmented`. **진행 중인 실험의 중간 보고**이며, 확정된 결론이 아니다.

이 문서는 [[PHASE2_DECIDER_GUIDE]] · [[AUGMENTED_FINAL]] · [[PLAN]] · [[REVIEW]] 스펙에 따라
**rango 1.3B 를 증강 프롬프트로 60k step 완전 재학습**한 기록이다. 확인된 사실과 추정을 구분해 쓰고,
실패한 실험도 그대로 남긴다.

---

## 0. 세 줄 요약

1. **loss 로는 증강 효과가 관측되지 않는다.** v1·v2 가 같은 step 에서 소수점 셋째 자리까지 겹치고(최근 절반 기울기 v1 −0.1426 / v2 −0.1425), 둘 다 원본 rango 대비 **+0.20~0.22** 로 같은 폭만큼 벌어진다.
2. **rand200 성공률은 학습 진행에 따라 오른다**(step 21k 27.5% → 40k 31.9%). 기준선 rango(33.5%) 와의 격차가 11.8%p → 4.8%p 로 좁혀졌으나 **아직 넘지 못했다.**
3. **loss 격차의 원인은 미확정.** 증강 탓이라는 근거가 약하고(v1↔v2 동일, 통제군 초반 400 step 차이 0.009), on-the-fly 검색 파이프라인 쪽이 유력하나 **직접 증명하지 못했다.**

## 1. 무엇을 했나

명세가 지정한 증강 3종을 프롬프트에 넣어 **rango 1.3B 를 처음부터 다시 학습**했다.

| # | 항목 | 근거 |
|---|---|---|
| 1 | **재랭킹** (premise 순서, 블렌드 α=5) | 기존 배선 `RERANK_PREMISES=1`, 7 데이터셋 검증(top-1 +11~18pp) |
| 2 | **[TYPES]** (goal 타입의 생성자/정의) | destruct·induction 구조 근거 |
| 3 | **[DEFINITIONS]** (goal 함수의 정의) | 함수 정의가 프롬프트에 0% = "불완전한 상태" 복원 |

명세는 [DEFINITIONS] 를 **2차**로 분류했으나, 사용자 지시로 1차와 함께 넣었다.
→ **대가**: REVIEW R5 가 경고한 "한번에 넣으면 귀속 불가" 가 그대로 발생했다. 최종 결과가 좋든 나쁘든
어느 레버의 효과인지 분리할 수 없다.

### 두 버전
| | **v1** | **v2** |
|---|---|---|
| [TYPES] | 생성자 **이름만** (`val := Vundef \| Vint \| ...`) | **정의문 전체**(인자 타입 포함, `Vint: int -> val`) + 재귀 depth1 |
| [DEFINITIONS] | 결론 식별자 시드 | 동일 시드 + 재귀 depth1 |
| 위치 | `[STATE]` 앞 | **맨 뒤**(응답 템플릿 직전) |
| 길이 제어 | 섹션별 독립예산 200 | 남은 자리 계산 후 **섹션만 절단**(예산 300) |

v2 의 [TYPES] 변경은 실패 로그 근거다 — `Expects a disjunctive pattern with 2/3 branches` 287건.
생성자 **인자 개수**를 알아야 destruct 패턴을 맞추는데, 이름만으로는 알 수 없다.

## 2. 구현

### 코드
```
src/tactic_gen/augment.py

  definitions()       v1 [DEFINITIONS] — 결론 전체 식별자 시드, 긴 정의는 시그니처만→그래도 길면 제외
  pick_def()          ★ 프로젝트별 정의 선택(이름 충돌 방지), 애매하면 주입 안 함
  types_v2/definitions_v2 + _expand/_shorten/_is_type_def   v2 재귀·축약 엔진
src/tactic_gen/tactic_data.py
  types_section/defs_section        v1 배선(독립예산, [STATE] 앞)
  augment_v2_section               v2 배선(맨 뒤, 남은 자리 계산 후 섹션만 절단)
scripts/build_func_defs.py         정의 인덱스 — 이름 80,716 / 정의 134,838 (26.5MB)
scripts/build_ind_constructors.py  생성자 인덱스 — 701 타입 (.v 폴백 추가: sentences.db 없는 서버 대응)
scripts/preflight_ft_augmented.py  학습 전 GO/NO-GO (타깃 플레이스홀더·주입률·길이)
scripts/warm_example_cache.py      예제 캐시 병렬 워밍(30 프로세스)
scripts/measure_premise_recall.py  검색 recall 측정
```

### 이름 충돌 처리 (v1·v2 공통, main 구현과의 차이)
같은 이름이 프로젝트마다 다르게 정의된다. `val` 은 CompCert 에서 `Inductive val := Vundef|Vint|...` 이지만
다른 21개 프로젝트에서는 `Definition val := Z.` 같은 **완전히 다른 것**이다.
→ 인덱스를 `{이름: {프로젝트: 정의}}` 로 만들고, goal 의 `file_name` 으로 **같은 프로젝트 정의를 우선** 선택.
못 고르면 **주입하지 않는다**(틀린 구조를 가르치느니 빼는 게 낫다).

### 학습 설정 (원본 rango parity)
| 항목 | 값 |
|---|---|
| 베이스 | deepseek-coder-1.3b-instruct + LoRA r=64 α=16 |
| LR / 스케줄 | 1e-3, **선형 감쇠, warmup 없음** (HF 기본값 — 원본도 동일, 실측 오차 0.00%) |
| max_steps | 60,000 (= 0.956 epoch, 2,009,606 예제) |
| 유효 배치 | 32 |
| hard_seq_len | 4,096 |
| 베이스 정밀도 | **bf16** (원본은 4bit QLoRA — 다른 점) |
| 데이터 경로 | **on-the-fly 검색** (원본은 전처리 DB, 현재 삭제됨 — 다른 점) |

★ `max_steps` 를 바꾸면 선형 감쇠 기준이 달라져 **같은 step 에서 lr 이 달라진다**. v1·v2 모두 60,000 으로
고정해 lr 궤적을 일치시켰다(통제군 실패 교훈, §5-2).

## 3. 결과

### 3-1. loss (같은 step 구간 평균)

| step | **v2** | **v1** | 원본 rango | v2−v1 | v1−rango |
|---|---|---|---|---|---|
| 0~2,000 | 0.8952 | 0.8628 | 0.7986 | +0.032 | +0.064 |
| 4,000~6,000 | 0.8067 | 0.8002 | 0.6517 | +0.007 | +0.149 |
| 8,000~10,000 | 0.7729 | 0.7656 | 0.5916 | +0.007 | +0.174 |
| 12,000~14,000 | 0.7556 | 0.7548 | 0.5456 | **+0.001** | +0.209 |
| 16,000~18,000 | 0.7304 | 0.7220 | 0.5160 | +0.008 | +0.206 |
| 20,000~22,000 | 0.7022 | 0.7027 | 0.4921 | −0.000 | +0.211 |
| 24,000~26,000 | 0.6860 | 0.6820 | 0.4702 | +0.004 | +0.212 |
| 28,000~30,000 | — | 0.6532 | 0.4490 | | +0.204 |
| 36,000~38,000 | — | 0.5979 | 0.4278 | | +0.170 |
| 40,000~42,000 | — | **0.5716** | 0.4214 | | +0.150 |
| rango 최종(58~60k) | — | — | **0.4085** | | |

**확인된 것**
- **v1 과 v2 는 구별되지 않는다.** 초반 +0.032 에서 12,000 부근 +0.001 로 수렴. 최근 절반 기울기가
  v1 −0.1426 / v2 −0.1425 로 소수점 넷째 자리까지 같다. → **프롬프트 설계 변경이 loss 에 영향 없음.**
- **둘 다 원본과 +0.20~0.22 로 같은 폭만큼 벌어진다.** 증강 방식을 바꿔도 격차가 동일 재현.
- v1 은 28,000 이후 격차를 +0.21 → +0.15 로 좁혔다(원본이 먼저 정체하기 때문).

**추정**(미검증): 격차가 증강 방식과 무관하게 재현되므로 원인은 증강이 아니라 **데이터 경로**(on-the-fly 검색)
쪽일 가능성이 높다. 그러나 원본의 전처리 DB 가 삭제돼 직접 비교가 불가능하다.

### 3-2. rand200 성공률 (600초 timeout)

| 모델 | 성공률 | 조건 |
|---|---|---|
| 기준선 rango (60k 완주) | **67/200 = 33.5%** | 워커 2 |
| v1 step 21,000 (35% 학습) | 35/139 = **25.2%** | 워커 16 |
| v1 step 40,000 (67% 학습) | 53/167 = **31.7%** | 워커 16 |
| v1 최종 (42.5k 중단) | 미측정 | |
| v2 | 미측정 (학습 중) | |

**같은 정리 부분집합 비교** (기준선과 겹치는 것만)

| | 우리 | 기준선 | 우리만 | 기준선만 |
|---|---|---|---|---|
| step 21,000 (139개) | 29+6 = 25.2% | 51 = 36.7% | 6 | 22 |
| step 40,000 (167개) | 48+5 = 31.7% | 61 = 36.5% | **5** | **13** |

**격차가 11.5%p → 4.8%p 로 좁혀졌다.** 다만 우리는 67% 학습 지점이고 기준선은 완주 모델이다.

### 3-3. 해결 집합 겹침 (step 40,000, 167개)
```
둘 다 성공     48  (28.7%)
우리만 성공     5  ( 3.0%)   [360, 700, 1327, 1344, 1544]
기준선만 성공  13  ( 7.8%)
둘 다 실패    101  (60.5%)

우리 단독   31.7%    기준선 단독  36.5%
★ 합집합    39.5%   ← 기준선보다 +3.0%p (5개 더 품)
Jaccard     72.7%
```

**학습이 진행되며 겹침이 커진다** — 이게 더 중요한 관찰이다.

| | 우리만 | 기준선만 | 합집합 | Jaccard |
|---|---|---|---|---|
| step 21,000 | 6 | 22 | 41.0% | **50.9%** |
| step 40,000 | 5 | 13 | 39.5% | **72.7%** |

기준선만 푸는 것이 22 → 13 으로 줄어(우리가 흡수) Jaccard 가 51% → 73% 로 올랐다.
반면 **우리만 푸는 것은 6 → 5 로 거의 그대로**다.
→ **추정**: 증강이 여는 "새로운 영역"이 넓지 않다. 두 모델은 학습이 진행될수록 같은 곳으로 수렴한다.

### 3-4. 실패 원인 분석 (step 40,000 로그, 실패 114 / 성공 53)
```
실패의 95% 가 600초 timeout — 그러나 "시간 부족"이 원인이 아니다:
  성공한 정리  탐색 중앙 12회   ← 풀리는 건 금방 풀린다
  실패한 정리  탐색 중앙 81회   ← 81번 해도 안 풀린다

생성한 tactic 의 74.6% 를 Coq 이 수용(VALID), COMPLETE 는 0
```
**Coq 거절 사유 top 5** (25.4% = 12,280건 중)
| 건수 | 사유 | 성격 |
|---|---|---|
| 308 | `Syntax error: ltac_use_default expected` | 문법 |
| 240 | `Not an inductive definition.` | **destruct 대상 오판** |
| 226 | `No product even after head-reduction.` | intro 대상 없음 |
| 209 | `No head constant to reduce.` | **unfold 대상 없음** |
| 287 | `Expects a disjunctive pattern with 2/3 branches` | **destruct 패턴 가지수 오류** |

→ **확인된 것**: 모델은 국소적으로 그럴듯한 tactic 을 잘 만들지만(75% 유효) 다단계 조합으로 QED 에
도달하지 못한다. 그리고 **프롬프트에 명시된 구조 정보조차 정확히 반영하지 못한다**
(생성자 목록을 줬는데도 가지 수를 틀림 287건). 이는 정보 부족이 아니라 **조합·정밀도 문제**이고,
[[COMPOSITION_IS_THE_WALL]] 의 예측("정보 주입은 +1~2pp 천장")과 일치한다.

### 3-5. v1 vs v2 프롬프트 CPU 실측 (CompCert gold 400개)

| | v1 | **v2** |
|---|---|---|
| 전체 토큰 중앙 | 1,741 | 1,846 |
| p99 / 최대 | 2,806 / 2,923 | 2,984 / **3,166** |
| **4096 초과** | 0건 | **0건** |
| 증강 섹션 크기 | 중앙 399, **최대 1,520** | 중앙 219, **최대 533** |
| 섹션 위치 | [STATE] 앞 | **[SCRIPT] 뒤 362/362** |

v2 는 남은 자리를 먼저 계산해 **증강 섹션만 잘라내므로** 최악값이 구조적으로 막힌다.
토크나이저가 `truncation_side='left'` 라 넘치더라도 정답 tactic 은 보존된다.

**depth 스윕** (재귀를 더 깊이 가면 이득이 있나)

| depth | [TYPES] | [DEFS] | 합계 | unfold 커버 | destruct 커버 |
|---|---|---|---|---|---|
| 0 | 33 | 48 | 90 | 74% | 49% |
| **1 (채택)** | 35 | 132 | **188** | 74% | 51% |
| 2 | 35 | 159 | 204 | 74% | 54% |
| 3 | 35 | 168 | 214 | 74% | **54%** (포화) |

→ unfold 커버는 depth 와 **완전 무관**(gold 가 unfold 하는 함수는 결론에 직접 등장 = 시드에서 잡힘).
destruct 커버만 +5%p 오르고 depth 2 에서 포화. **depth 1 이 비용/이득 변곡점.**

**main 구현(b1dd53a)과의 [DEFINITIONS] 비교** — 시드 방식이 결정적

| | main | ours |
|---|---|---|
| 시드 | `f(` 형태 또는 대문자 | 결론의 모든 식별자 |
| **gold unfold 적중률** | **21.6%** (25/116) | **70.7%** (82/116) |
| 평균 토큰 | 69 | 82 |

main 정규식 `([A-Za-z_][\w'.]*)\s*\(` 은 함수 뒤에 괄호를 요구하는데, Coq 관용구는 `f x` 다.
`succ (pred x) = x` 에서 정작 unfold 대상인 `pred` 를 놓친다. → **[DEFINITIONS] 는 우리 시드가 우월.**

## 4. 진행 중 잡은 인프라 문제 8건

없었으면 60k step 이 통째로 헛돌거나 시작조차 못 했을 것들이다.

| # | 문제 | 증상 | 수정 |
|---|---|---|---|
| 1 | **transformers 5.x 비호환** | `train_decoder.py` 가 **실행 자체 불가**. `evaluation_strategy`, `Trainer(tokenizer=)` 개명 | 버전 감지해 `eval_strategy`/`processing_class` 선택 |
| 2 | **`save_total_limit` 이 마일스톤 삭제** | 오래된 것부터 지워 5,000 배수 보존이 깨짐 | `null` 로 두고 `CheckpointRotationCallback` 이 회전(5,000 배수 영구, 그 사이 1,000 단위는 다음 마일스톤에서 삭제) |
| 3 | **ExampleCache 파일단위 빌드** | 캐시 미스 시 그 파일의 **모든 proof×step**(수천 개)을 빌드 → dataloader 가 수 시간 정지 | 600 쌍 초과 파일은 **요청된 예제만** 생성. 워밍 스크립트도 동일 |
| 4 | **검색 디버그 print** | `lm_example.py` 가 예제마다 goal·쿼리·top5 를 stdout 에 덤프 → **예제당 13초** | `SHOW_RETRIEVAL=1` env 가드. **13초 → 0.05초** |
| 5 | **패딩 낭비** | 모든 예제를 4,096 까지 패딩(실제 중앙 1,700) → 연산 절반 이상 낭비 | `DYNAMIC_PADDING=1`. **6.4 → 2.66 s/step (2.4배)**. loss 는 수학적으로 동일(pad 는 mask/-100 제외) |
| 6 | **DDP 랭크 경쟁** | 한 랭크가 만든 output_dir 을 다른 랭크가 "이미 존재"로 보고 즉사. NFS ctime 캐시까지 겹침 | rank0 만 생성, 판정 기준을 '체크포인트 존재'로 변경 |
| 7 | **깨진 체크포인트** | 저장 중 죽으면 `trainer_state.json` 없는 반쪽이 남고, 재개가 **영구 실패** | 최신부터 검사해 완전한 것 사용, 손상본은 `broken-checkpoint-N` 으로 격리 |
| 8 | **255자 파일명** | 캐시 원자적 쓰기의 `.tmp<pid>` 접미사가 길이 한계 초과(해당 파일 195개) | tmp 이름을 짧게(`.tmp-<pid>-<hash>`) |

추가: **런처까지 함께 죽는 경우**(세션 종료·프로세스그룹 kill)는 스크립트 내부 재시도 루프가 못 잡는다.
실제로 v2 가 687 step 에서 그렇게 죽어 2시간 40분을 잃었다 → `all_log/v2_watchdog.sh` 감시견 추가
(2분마다 확인, 4분 연속 부재면 자동 재기동. 평가 중이면 GPU 를 뺏지 않도록 감시를 쉰다).

## 5. 미해결 · 한계

### 5-1. loss 격차(+0.15~0.22)의 원인 미확정
v1↔v2 가 동일하므로 증강 탓이라는 근거는 약하다. 남은 후보는 **on-the-fly 검색**인데, 원본의 전처리 DB 가
삭제돼 직접 비교가 불가능하다. 정황 증거:
- 학습 예제의 **16% 가 premise 0개**, 36% 가 10개 이하 (프로젝트별 편차: corn/gaia 50개 vs UniMath 4개)
- **gold lemma recall 23.2%** (CompCert 롤아웃 32.2%)
- 다만 `premise_filter: proj-thm`(누수 방지)은 **원본도 같은 제약**을 받았고, 해당 프로젝트가 DB 에
  누락된 것도 아니다(UniMath 10,741 문장 수록). → 이 정황만으로 단정 불가.

### 5-2. 통제군 실험 — 설계 결함으로 중단
증강만 끄고 2,000 step 학습해 비교하려 했으나, conf 에 `max_steps: 2000` 을 넣어 **LR 이 2,000 에서 0이 되도록
감쇠**했다. 본 학습(60,000 기준)과 같은 step 에서 lr 이 달라져 비교 불가.
```
step 500 : 본학습 9.91e-4  vs  통제군 7.40e-4
step 1000: 본학습 9.83e-4  vs  통제군 4.91e-4
```
**LR 이 아직 비슷한 첫 400 step 만** 보면: 증강 ON 0.9331 / OFF 0.9245 / 원본 0.9064 →
증강 유무 차이 **0.009**(원본과의 차이보다 작음). 표본이 작아 참고용.
**재실행하려면 `max_steps: 60000` 을 유지하고 2,000 step 에서 끊어야 한다.**

### 5-3. ablation — temperature 1.0 샘플링으로 판정 불가
"우리만 푼 6개"가 정말 [TYPES]/[DEFINITIONS] 덕분인지 검증하려 했다. 헤더는 유지하고 내용만 `(none)` 으로
비워 **포맷 고정 + 정보만 제거**(그냥 끄면 OOD 라 증거가 못 됨).

| 정리 | 원래 | full(내용 그대로) | ablated(내용 비움) |
|---|---|---|---|
| 360 / 467 / 700 | 성공 | **실패** | 실패 |
| 702 | 성공 | 성공 | **성공** |
| 1327 / 1344 | 성공 | 성공 | 실패 |
| | | **3/6** | **1/6** |

**full 조건이 6개 중 3개만 재현했다.** 원인은 생성이 확률적 샘플링(`do_sample=True, temperature=1.0`).
노이즈 수준이 50% 인 위에서 3/6 vs 1/6(차이 2건)은 우연과 구분되지 않는다.
702 가 ablated 에서도 풀린 것만 확실한 정보 — 오히려 "주입 없이도 되는 정리"라는 반대 증거다.
**제대로 하려면 조건당 5회 반복이 필요하다.** (개별 정리 단위 분석은 신뢰 불가, 137개 표본의 성공률
비교는 변동이 평균화되므로 유효.)

### 5-4. destruct 대상의 71% 는 이미 goal 에 있다 (설계 재검토)
gold destruct/induction 285건 분류:

| 유형 | 비율 | 프롬프트에 이미 있나 |
|---|---|---|
| 복합식 `destruct (E)` | 43.9% | **64.2% 가 goal 에 등장** |
| 가설변수 (도메인 타입) | 27.7% | 가설에 `l : loc` 형태로 있음 |
| 가설에 없는 이름 | 24.9% | (숫자·파싱 실패 포함) |
| 가설변수 (stdlib) | 3.2% | 모델이 이미 앎 |

→ **"무엇을 destruct 할지"는 주입이 불필요하다.** 필요한 것은 **패턴**(생성자 개수·인자)이고, 그건 goal 에
안 보인다. v2 가 생성자 시그니처를 넣는 이유가 이것.
복합식 중 goal 에 없는 35.8% 는 대부분 **lemma**(`Rle_or_lt`, `Zle_or_lt` = 삼분법)라 함수 정의 인덱스로는
해결 안 되고, 이미 [PREMISES] 검색이 담당하는 영역이다(8.1% 는 premises 에 있는데도 못 씀).
→ **복합식 보강은 수익이 낮다고 판단해 착수하지 않음.**

### 5-5. "v2 가 더 낫다"는 **미검증**
v2 는 "더 잘 설계된 프롬프트"이지 "더 정확한 모델"이 아니다. 확인된 것은 프롬프트 품질의 대리지표
(생성자 인자 제공, 길이 보장, gold unfold 적중 70.7%)뿐이고, **성능 비교는 완주 후 rand200 이 필요하다.**
loss 로는 v1 과 구별되지 않으며, 프롬프트가 중앙 +105 토큰 늘어나므로 정보가 도움이 안 되면 노이즈다.

### 5-6. 세 학습이 완전히 동일 조건은 아니다
프롬프트 외에 **베이스 정밀도**(bf16 vs 4bit)와 **데이터 경로**(on-the-fly vs 전처리 DB)가 다르다.
따라서 "우리 vs 원본" 격차를 증강 탓으로 돌릴 수 없다.

```bash
# 0) 인덱스 빌드 (CPU, 1회)
python3 scripts/build_ind_constructors.py CoqStoq data/ind_constructors_clean.json   # 701 타입
python3 scripts/build_func_defs.py data/coq-dataset/sentences.db data/func_defs.json # 80,716 이름

# 1) 코퍼스 tmpfs 스테이징 + 예제 캐시 워밍 (필수 — 안 하면 dataloader 가 GPU 를 굶긴다)
#    코퍼스 14GB, 캐시 30GB, 30 프로세스로 약 2.5시간
python3 scripts/warm_example_cache.py all_log/ft_rango_augmented_conf.yaml 30

# 2) 사전점검 (GO/NO-GO — 타깃 플레이스홀더·주입률·프롬프트 길이)
RERANK_PREMISES=1 INJECT_TYPES=1 INJECT_DEFS=1 \
  python3 scripts/preflight_ft_augmented.py all_log/ft_rango_augmented_conf.yaml

# 3-a) v1 학습
bash all_log/ft_rango_augmented.sh          # 2GPU DDP, 자동재개, 체크포인트 회전

# 3-b) v2 학습
nohup setsid bash all_log/run_augmented_v2_ddp.sh </dev/null >/dev/null 2>&1 &
nohup setsid bash all_log/v2_watchdog.sh    </dev/null >/dev/null 2>&1 &   # 감시견 필수

# 4) 평가 — ★ 학습과 **같은 env** 여야 한다(다르면 OOD 로 성능이 실제보다 낮게 나옴)
#    v1: RERANK_PREMISES=1 INJECT_TYPES=1 INJECT_DEFS=1
#    v2: + AUGMENT_V2=1 HARD_SEQ_LEN=4096 TYPES_TOKENS=300 DEFS_TOKENS=300
CKPT=<체크포인트> WPG=8 TIMEOUT=600 bash all_log/pause_eval_resume.sh
```

**주의사항**
- 기존 rand200 결과는 모두 **600초** 기준이다. 300초로 재면 비교가 성립하지 않는다.
- 워커 수도 confound 다(기준선 w2, 우리 중간평가 w16). 최종 비교는 **600초·워커 2** 로 맞출 것.
- 백그라운드 실행은 `nohup setsid ... </dev/null` + `disown -a` 로 **PPID 1** 을 확인할 것.
  세션에 묶이면 함께 죽는다(실제로 겪음).
