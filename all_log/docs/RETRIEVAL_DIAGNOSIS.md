# 검색 결손 진단 — gold lemma 는 왜 프롬프트에 없는가

작성 2026-08-18 (KST) · 브랜치 `rango-augmented` · v8 학습은 보류 중

---

## 0. 한 줄 요약

**개선안을 찾았다: gold 포함률(R@50) 61.1% → 69.6%, 상위 정확도(R@10) 32.8% → 44.8%.**
방법은 **RRF(tfidf + 결론구조 + 이름subword)** 이며 lemma 이름 없이도 R@10 +12pp 가 나온다(§5.6).
아직 실험대에서만 확인됐고 파이프라인에 넣지 않았다.

**필요한 lemma 를 전부 갖춘 tactic 은 35.8% 뿐이고, 원인의 압도적 다수는 retriever 성능이다
(38.4%). 수집 로직 구멍은 2.9% 로 작다. 이건 원본 rango 부터 있던 문제이며, 우리 변경
(재랭킹·타입주입·정규화)이 만든 것이 아니다.**

---

## 1. 왜 이걸 팠나

학습 타깃이 쓰는 lemma 가 프롬프트에 없으면, 그 예제는 **읽을 수 없는 이름을 뱉으라고
가르친다**. 즉 검색 활용이 아니라 **암기**를 훈련한다.

v8 은 이름을 익명화해 암기 경로를 막는다. 그런데 정보가 없는 채 기억만 막으면 **풀 수 없는
문제**가 된다. 게다가 익명화는 문제를 더 뾰족하게 만든다.

- 프롬프트에 **있는** premise → `L0, L1, …` 로 익명화
- 프롬프트에 **없는** lemma → 매핑할 대상이 없어 `Ropp_0` 그대로 타깃에 남음

결과적으로 모델에게 *"익명 이름은 프롬프트에서 읽고, 실명은 외워서 써라"* 라는 **분리 신호**를
주게 된다. 익명화가 겨냥한 바로 그 습관을 오히려 선명하게 만든다.

## 2. 결론 먼저

### 2.1 실제로 쓸 수 있는 tactic 은 35.8%

TRAIN 5,000 예제 중 lemma 를 쓰는 tactic 670건, top50 기준.

| | 전부 있음 | 일부만 | 하나도 없음 | n |
|---|---|---|---|---|
| lemma 1개 | 42.0% | 0.0% | 58.0% | 538 |
| **lemma 2개+** | **10.6%** | 25.8% | 63.6% | 132 |
| **합계** | **35.8% ±3.6pp** | 5.1% | 59.1% | 670 |

tactic 의 **19.7% 가 lemma 를 2개 이상** 쓰는데, 하나만 빠져도 못 쓴다. 그쪽은 10.6% 만
필요한 것을 다 갖췄다 — 사실상 전멸이다.

### 2.2 원인은 retriever (38.4%), 수집 로직 아님 (2.9%)

TRAIN 5,000 예제 · gold 가 lemma 를 쓰는 589건 · top50 · 첫 lemma 기준.

| 분류 | 비율 | 뜻 |
|---|---|---|
| ① top50 안에 있음 | 40.6% ±4.0 | 정상 |
| **② 풀엔 있는데 검색이 못 뽑음** | **38.4% ±3.9** | **retriever 성능** |
| ④ 데이터셋에도 없음 | 12.7% ±2.7 | 표준/외부 라이브러리 |
| ③b 다른 프로젝트에만 있음 | 5.4% ±1.8 | 애초에 접근 불가 (정상) |
| **③a 같은 프로젝트인데 풀에 없음** | **2.9% ±1.4** | **수집 로직 구멍** |

**retriever 대 수집 로직이 13배 차이**이고 신뢰구간이 겹치지 않는다.

### 2.3 lemma 개수로 나누면 복수 쪽이 전면적으로 나쁘다

개별 lemma 의 소재 (같은 5,000 예제).

| 분류 | lemma 1개 (538개) | lemma 2개+ (366개) |
|---|---|---|
| ① top50 에 있음 | 42.0% | **20.2%** |
| ② retriever 가 놓침 | 36.8% | **43.4%** |
| ③a 수집 로직 | 2.4% | 2.5% |
| ③b 접근 불가 | 6.1% | 7.4% |
| ④ 데이터셋 밖 | 12.6% | **26.5%** |

② 의 출처가 뒤집히는 것이 시사적이다.

- lemma 1개 : Coq 표준 60.6% · 같은 프로젝트 39.4%

여러 lemma 를 엮는 tactic 은 **그 프로젝트 고유 정리들을 조합**하는 경우가 많다.
pretraining 기억으로 메울 수 없는 부분이다.

## 4. TF-IDF 가 지는 이유

`Zlt_le_succ` — goal `Z.succ 0 <= a`, lemma `n < m -> Z.succ n <= m`.
**단어는 겹친다.** 그런데 풀 9,957개 중 `Z.succ`·`<=` 를 포함한 문장이 수백 개라 변별력이 없다.

`gupaco5_mon` — top50 이 `gpaco5_*`, `_paco_pre*` 로 채워졌다. **철자가 비슷한 것에 밀렸다**
(`g`**`u`**`paco5` vs `gpaco5`).

즉 TF-IDF 는 *"무엇과 무엇이 단일화되는가"* 를 모른다. 단어 겹침은 구조적 적용가능성의
대리지표로 약하다.

## 5. 해법 후보

| 방법 | 겨냥 | 비용 | 상태 |
|---|---|---|---|
| **Coq SearchPattern** | ②38.4% + ④12.7% = **51.1%** | 30~70ms/노드 | **실증 완료 (5/5 회수)** |
| 역색인 + 구조 매칭 | ② 38.4% | 인덱스 구축 | Coq 내부 동작의 재구현 — 중복 |
| 학습형 dense retriever | ② 38.4% | 학습 필요 | 근본적이나 장기 |
| 후보 수 늘리기 | — | 토큰 | **답 아님** (100→1000 으로 10배 늘려 +5.9pp) |
| 프롬프트 토큰 늘리기 | — | — | **답 아님** (후보의 93.8% 가 이미 실림) |

### 5.1 SearchPattern 실증

생성한 질의를 실제 Coq(coq-lsp) 에 날려 확인.

| gold | 시간 | 결과 | 가장 좁은 질의 |
|---|---|---|---|
| `Zlt_le_succ` | 78ms | 3건 | `SearchPattern ((Z.succ _) <= _)` |
| `Z.mul_comm` | 30ms | 13건 | `SearchPattern ((_ * _) = (_ * _))` |
| `rev_length` | 41ms | 32건 | `(length (rev _)) = (length _)` → **1건** |
| `Z.pow_add_upper` | 168ms | 3건 | `((_ + _) ^ _) <= …` → **1건** |
| `app_length` | 43ms | 26건 | `(length (_ ++ _)) = …` → **1건** |

**5/5 회수.** 깊은 패턴이 1건으로 정확히 집어낸다. `Zlt_le_succ` 는 TF-IDF 가 후보
1000개 안에도 못 넣던 바로 그 lemma다.

Coq 은 **그 시점에 실제로 로드된 모든 것**을 보므로, 데이터셋 풀에 없는 ④(12.7%)까지 잡는
유일한 방법이다.

### 5.2 SearchPattern 의 두 가지 우려 — 결과 폭발 · 복잡한 apply

#### (1) 결과가 너무 많이 나오지 않나 → **실측상 안 나온다**

프롬프트에 실리는 premise 는 중앙 21개인데 넓은 질의는 수백 건을 뱉는다
(`SearchPattern (_ <= _)` → 192건). 케이스 10개로 잰 결과:

| 상한 K | 회수율 | 반환 중앙 | 반환 최대 |
|---|---|---|---|
| 10 | 70% | 10건 | 22건 |
| 50 | 70% | 13건 | 25건 |
| 무제한 | 70% | 13건 | 25건 |

**상한을 걸든 안 걸든 중앙 13건 · 최대 25건.** 그리고 gold 를 회수한 7건 **전부가
1~2번째(가장 좁은) 질의**에서 나왔다. 추상화 사다리가 좁은 것부터 가기 때문이다.

    1건   (length (rev _)) = (length _)     ← gold 여기
    5건   (length _) = (length _)
    20건  length _ = _                      ← 넓지만 마지막

다만 우려가 근거 없지는 않다. `length _ = _`(20건), `(Z.max _) _ = _`(22건),
`(In _) _`(16건) 처럼 head 가 흔하면 20건대가 나와 **한 질의가 정원 21개를 다 먹는다**.
K=10 이면 회수율 손실 없이 중앙 10건으로 눌린다 → **상한 정책은 유지한다**.

#### (2) 패턴으로 못 찾는 복잡한 apply 가 있지 않나 → **있다. 다만 성격이 다르다**

TRAIN apply/rewrite 계열 357건을 정적으로 분류했다.

| 분류 | 비율 | 실제 성격 |
|---|---|---|
| OK | 60.5% ±5.1 | 질의 생성 가능 |
| A goal 에서 질의가 안 나옴 | 17.9% ±4.0 | **파서 한계** (원리적 한계 아님) |
| D `apply X in H` | 13.7% ±3.6 | **미구현** (가설 질의를 만들면 됨) |
| E eapply | 5.9% ±2.4 | **오분류 — 실제로는 정상 작동** |
| B lemma 결론 head 가 메타변수 | 2.0% ±1.4 | 절반은 양방향 질의로 해결 |

**★ `OK` 의 정확한 의미** — 아래 네 조건을 통과했다는 뜻일 뿐이다.

1. goal 결론이 파싱되고, 지역이름을 지운 뒤에도 남는 구조가 있어 **질의가 생성됨**
2. gold lemma 결론의 최상위 자리가 메타변수가 아님
3. `apply X in H` 가 아님
4. `eapply` 가 아님 ← **이 조건은 잘못 넣은 것**(아래 E 참조)

**`OK` 는 "실제로 gold 를 찾았다"가 아니다.** 이 측정은 Coq 에 질의를 날리지 않았다.
정적 분석으로 *"패턴 방식이 원리적으로 배제되지는 않는다"* 만 본 **필요조건**이다.
질의를 만들 수 있어도 결과가 0건이거나 gold 가 없을 수 있다. 실제 회수율은 표준 라이브러리
기반 인공 케이스 10건에서 **70%** 였고, 실제 프로젝트 goal 에서는 아직 안 쟀다.

##### A — goal 에서 질의가 안 나옴 (17.9%)

"지역변수뿐" 이라고 이름 붙였으나 사례를 보니 **둘 다 파서 한계**였다.

A-1. **파싱 실패** — 람다가 들어 있으면 트리를 못 만든다.

    goal : sumList (filter P (getSupport c)) (fun b0 : A => evalDist c b0 * …) + sumList (…
    파스 : None

A-2. **커스텀 notation 미지원** — CoRN 의 `[<=]` 를 불투명 덩어리로 처리해
`b` 가 함수이고 `[<=]` 가 인자인 것처럼 잘못 파싱한다.

    goal : b [<=] b
    파스 : ('app', ('app', ('id','b'), ('opq','[ <= ]')), ('id','b'))

`[<=]` 를 중위 연산자로 읽었다면 `SearchPattern (_ [<=] _)` 가 나왔을 것이다.
프로젝트별 `Notation` 선언을 읽어 연산자 표에 넣으면 해결된다.

##### D — `apply X in H` (13.7%)

goal 이 아니라 **가설을** 변형한다. goal 결론에는 정보가 없다.

    tactic : apply M.F.P.F.not_find_in_iff in HDisjCalls.
    goal   : False
    질의   : (없음)

**원리적 한계가 아니다** — 대상 가설의 모양으로 질의를 만들면 된다. 구현이 없을 뿐.

##### E — eapply (5.9%) — **오분류**

`SearchPattern` 은 결론 모양만 보므로 evar 유무와 무관하다. 실제로 잘 작동한다.

    tactic     : eapply oc_EqDec; eauto.
    goal       : EqDec B
    생성 질의  : SearchPattern (EqDec _).
    gold lemma : … -> EqDec C          ← 이 질의에 매칭된다

**즉 5.9% 는 OK 에 합쳐야 한다.** "eapply 면 무조건 실패" 로 분류한 것이 틀렸다.

##### B — lemma 결론 head 가 메타변수 (2.0%)

    gold  : Theorem plus_n_O : forall n:nat, n = n + 0.     결론 `n = n + 0`, 메타변수 {n}
    goal  : n + 0 = n
    질의  : SearchPattern ((_ + 0) = _).

`plus_n_O` 의 등식 **왼쪽은 그냥 `n`**(메타변수)이라 이 질의와 안 맞는다.
`SearchPattern (_ = (_ + 0))` 으로 물어야 잡힌다 → **등식 질의를 양방향으로** 만들면 해결.
결론이 `?P x` 처럼 술어 자리 자체가 변수인 고차 경우만 남는다.

##### 정정된 그림

**지금 구현 기준 약 66%(OK 60.5 + E 5.9)가 통하고, 진짜 원리적 사각지대는 2% 보다 작다.**
나머지는 전부 구현을 고쳐야 하는 부분이다: 커스텀 notation 파싱 · 가설 방향 질의 ·
양방향 등식 질의.

#### (3) 부수 발견 — 질의가 지나치게 구체적일 수 있다

goal 이 거대하면 이런 질의가 나온다.

    SearchPattern (((((((((AbsIR ((((((_ (S _)) ((((_ _) _) _) _)) _) _) _) …

0건이 나올 것이 뻔하다. **질의 크기 상한**도 필요하다.

### 5.3 retrieval 쿼리는 goal 만 보지 않는다 — 오히려 너무 많이 본다

```python
class BasicContextFormat:                    # premise_selection/premise_formatter.py
    def format(step, proof):
        partial_proof = proof.proof_prefix_to_string(step)   # 지금까지 쓴 증명 전체
        goal_strs = [f"Goal {i+1}:\n{goal.to_string()}"      # 남은 goal 전부(가설 포함)
                     for i, goal in enumerate(step.goals)]
        return f"{partial_proof}\n\n{goal_str}"
```

검색 쿼리 = **지금까지의 증명 스크립트 + 남은 goal 전부**. 현재 goal 의 결론은 그중 작은
일부다. TF-IDF 에서 쿼리가 길면 핵심 신호가 희석되고, 가설의 지역 변수명(`H`, `H0`, `a`)과
이미 쓴 tactic(`intros`, `induction`)이 노이즈로 들어간다.

**②(38.4%) 의 더 큰 원인일 수 있다.** 데이터 재생성 없이 **쿼리만 바꿔** 검증 가능하다.
아직 안 쟀다.

### 5.4 강화학습은 부적합

**retrieval 에는 정답 라벨이 이미 있다** (gold tactic 이 쓴 lemma). 라벨이 있는 문제에 RL 을
쓰는 건 정보를 버리는 것이다. 표준 해법은 contrastive 지도학습이다.

또한 PPO critic 이 희소 보상에서 `explained_var≈0` 으로 실패한 전례가 있는데
([[ppo-bigscale-pending]]), retrieval 보상은 그보다 더 희소하다(1만 개 중 1개).

RL 여지가 있는 유일한 지점은 *"어떤 질의를 던질까"* 인데, 지금은 추상화 사다리(깊이 3→2→4→1)
규칙으로 충분하다.

### 5.5 gold 주입은 100% 면 반대

학습에서 gold 를 항상 넣으면 모델은 *"정답은 항상 목록에 있다"* 를 배운다. 추론 시 실제
recall 은 35.8% 이므로, 모델은 없는 정답을 목록에서 억지로 고르게 된다 — **암기 문제를
환각 문제로 바꿀 뿐이다**.

**핵심은 학습 시 recall 과 추론 시 recall 을 맞추는 것.** 순서는 이렇다.

1. 검색을 먼저 고치고 **학습·추론 양쪽에 동일 적용**
2. 그래도 남는 결손에만, 필요하면 실제 recall 과 비슷한 비율로 **부분 주입**

gold 주입이 정당한 용도는 **진단**이다 (gold prefix 실험처럼 상한 측정).

## 5.6 ★ 실제 개선 — gold 포함률 61.1% → 69.6%

여러 스코어링 방식을 같은 자로 재서(TRAIN 424건, 오차 ±4.6pp) 찾은 결과다.
`scripts/research_retrieval.py`(쿼리·premise 표현) · `scripts/research_structural.py`(구조·RRF).

| 방식 | R@10 | R@20 | R@50 | MRR | lemma 이름 |
|---|---|---|---|---|---|
| baseline tfidf | 32.8% | 48.1% | 61.1% | 0.159 | 씀 |
| 이름subword | 37.3% | 48.3% | 63.0% | 0.167 | 씀 |
| **RRF(tfidf,C') K=30** | **44.8%** | 52.1% | 63.9% | 0.221 | **안 씀** |
| **RRF(tfidf,C')+E 가산** | 42.9% | 50.7% | **64.9%** | 0.217 | **안 씀** |
| **RRF 3-way +A'E 가산** | 44.3% | **55.7%** | **69.6%** | 0.235 | 씀(보조) |

프롬프트에 실리는 premise 가 중앙 21개이므로 **R@20 이 실질 지표**, `num_premises: 100`
기준으로는 R@50 이 상한이다.

### 신호들

| 기호 | 신호 | lemma 이름 |
|---|---|---|
| A | 적용가능성 (`applicable.py` 단일화, 0/1) | 안 씀 |
| A' | 매칭된 부분항 크기 / goal 크기 (연속값) | 안 씀 |
| B | 결론 최상위 head 일치 | 안 씀 |
| C | 연산자 집합 Jaccard | 안 씀 |
| C' | **결론 부분항 head 의 IDF 가중 코사인** | 안 씀 |
| D | 결론 크기·깊이 유사도 | 안 씀 |
| E | lemma **가설부** head 가 goal 가설블록에 있나 | 안 씀 |

`C'` 가 핵심이다. 함수 이름(`Z.succ`·`length`)은 쓰지만 **lemma 이름은 안 쓴다** — 전역
상수이고 v8 정규화 대상이 아니다(정규화는 lemma 이름 L#, 주입정의 T#/f#, 생성자 C# 만 바꾼다).
TF-IDF 와 다른 점은 **결론에서만** 뽑고 부분항 위치를 본다는 것이다(가설부 노이즈 없음).

### 왜 RRF 인가 — 실패 방식이 다른 랭커를 합친다

| 랭커 | 어디서 지나 | 단독 R@50 |
|---|---|---|
| tfidf | 단어가 안 겹치면 (`Zlt_le_succ` 놓침) | 61.1% |
| C' | 결론 파싱 실패분이 꼬리로 밀림 | **46.0%** |
| 이름subword | 작명 관례가 없는 프로젝트 | 63.0% |

**점수를 더하면 스케일이 큰 쪽에 눌린다**(`tfidf + A'×15 + C'×25` → 61.1%, 개선 0).
순위의 역수를 더하면(RRF, K=30~60) 서로의 실패를 메운다. `C'` 단독은 baseline 보다
나쁜데도 합치면 최고가 되는 것이 그 증거다.

### 이진 신호는 랭킹에 못 쓴다

`A 적용가능성만` 은 R@50 **3.1%** 다. 선택성이 56% 라 후보의 절반이 동점이 되어 순서를
정할 수 없다. 풀 전체에 걸면 더 나빠진다(상위 1200개 제한 시 11.2% → 전체 3.1%).
**필터가 아니라 가산으로만** 쓴다 (`+A'E` 가 +0.5pp 기여).

### 통하지 않은 것들 (기록)

| 시도 | R@50 | |
|---|---|---|
| premise 를 **결론만**으로 | 40.0% | -16pp. 정보가 너무 적다 |
| bm25 로 교체 | 44.0% | -12pp |
| goal 만 / goal×3 / goal×5 가중 | 56% 동일 | 쿼리 가중은 무효 |
| 순수 구조 A+B+C+D | 26.2% | 변별력 부족 |
| RRF 가중 (C'×2) | 50.7% | C' 를 키우면 오히려 나빠진다 |

### 비용

137ms/건 (baseline 53ms 의 2.6배). `prem_struct` 가 lru_cache 되어 프로젝트 내에서
재사용되므로 실제 데이터 생성에서는 더 낮다.

### 아직 안 한 것

이 개선은 **실험대에서만** 확인됐다. `SparseClient.get_premise_scores` 에 넣어 학습·추론
양쪽에 적용하고, 그때 "필요한 lemma 를 전부 갖춘 tactic 35.8%" 가 얼마나 오르는지 재야 한다.

## 5.7 발견 — 정규화가 추론 경로에 적용되지 않는다

| 경로 | 함수 | 정규화 |
|---|---|---|
| 학습 | `collate` (tactic_data.py:750) | **있음** (`NORMALIZE_RATE=0.5` → 절반만) |
| 추론 | `collate_input` (model_wrapper.py:227) | **없음** |

즉 v8 은 학습에서 절반을 `L0,L1,…` 로 보고 추론에서는 원본 이름을 본다. **학습·추론 분포가
다르다.** `RATE=0.5` 가 이 불일치를 완화하는 설계일 수는 있으나, 그렇다면 정규화 효과가
반감된다. v8 을 재개하기 전에 판단이 필요하다.

(검색 자체는 정규화 **전** 단계이므로, 이름 기반 검색 신호는 이 문제와 무관하게 유효하다.)

## 7. 구현한 것

### 7.1 `src/tactic_gen/applicable.py`

Coq 항 파서(Pratt) + 일차 단일화. *"닮았나"* 가 아니라 *"**되나**"* 를 판정한다.

- `apply` : premise 결론이 goal 결론 전체와 매칭되나
- `rewrite` : 등식 한 변이 goal 의 **부분항**과 매칭되나
- 파싱 실패 시 **보수적으로 통과** (gold 를 떨어뜨리면 안 되므로)

**성능**: 재현율 90% · 파싱 성공 99.6% · 선택성 56.1%

**실측으로 잡은 함정** (재현율 32% → 60% → 86% → 90%)

| 버그 | 증상 | 수정 |
|---|---|---|
| `<->` 를 문자열 `->` 로 자름 | `A <-> B` 가 가설 `A <` + 결론 `B` | 토큰 단위 분리 |
| `[GOAL]` 로 이어진 여러 goal 중 **마지막**을 봄 | 엉뚱한 goal 과 매칭 | 첫 goal 만 |
| `(s,d) :: m2` 가 `s` 로 뭉개짐 | 괄호 안 파싱 실패 시 소비분만 버림 | 균형 지점까지 건너뛰고 불투명 항으로 |
| `\|\|` 를 레벨 85 로 (Prop 의 `\/` 와 혼동) | `a = b \|\| c` 가 `(a=b) \|\| c` | bool 연산은 레벨 50/40 |
| notation ↔ 함수 이름 | `beta ^ e` 와 `Zpower n k` 를 다르게 봄 | 정규형으로 통일 |
| 화살표 중간 `forall` 변수 누락 | `apply X with y` 계열 실패 | 청크마다 바인더 수집 |
| `%R` scope 주석 | `0 % R` 로 파싱 | 토큰화 전 제거 |

회귀 테스트 `scripts/test_applicable.py` — **33건 전부 통과**.

### 7.2 재랭킹 통합

`tactic_data.rerank_premises` 에 `APPLICABLE_RERANK=1` / `APPLICABLE_BETA=30`.

점수 = 원순위 prior + α×타입점수 + **β×적용가능성** (α=5 고정)

| β | top1 | top5 | top10 | top20 |
|---|---|---|---|---|
| 0 (현재) | 34.9% | 63.6% | 76.7% | 92.2% |
| 20 | 47.3% | 69.8% | 80.6% | 96.1% |
| **30** | **46.5%** | **70.5%** | **81.4%** | **96.9%** |
| 50 | 44.2% | 66.7% | 78.3% | 95.3% |

프롬프트에 실제로 실리는 premise 가 중앙 21개이므로 **top20 이 실질 지표** → β=30.

**필터가 아니라 가산**이다. 판정 재현율이 90% 라 10% 는 gold 를 잘못 떨어뜨린다.

**비용**: step(16예제)당 25.3ms = 관측 step 시간(4.6~6.1s)의 **0.51%**. 결정적.
49% 예제에서 상위 8개 순서가 실제로 바뀐다.

### 7.3 `src/tactic_gen/search_query.py`

goal → SearchPattern 질의 생성기. `applicable.py` 파서를 재사용해 트리를 다시 문자열로 찍되
깊이 아래를 `_` 로 접는다.

**추상화 사다리**: 깊이 3 → 2 → 4 → 1 (좁은 것부터)

**함정**: goal 의 **지역 변수를 반드시 `_` 로** 바꿔야 한다. `SearchPattern (Z.succ 0 <= a)`
의 `a` 는 이 증명 안에서만 사는 변수라 어떤 lemma 에도 없다 → 항상 0건.

## 8. 방법론과 한계

### 측정 방법

1. `LmDataset` 으로 TRAIN split 앞 N개 (shuffled index — 학습이 보는 순서와 동일)
2. gold tactic 에서 lemma 이름 추출
   - `;` 앞 첫 조각만 (전체 버전은 `all_gold_lemmas`)
   - ` in ` 뒤(대상 가설) 제거
   - tactic 키워드·지역가설 패턴·짧은 소문자 제외
   - **proof state 가설 블록에 선언된 이름이면 제외** (지역 가설)
3. 세 곳에서 차례로 찾아 분류: top-K → `avail_premises` 풀 → `sentences.db`(582,037행)

### 검증

분류가 맞는지 원자료를 통째로 덤프해 확인했다.

| 케이스 | 확인 |
|---|---|
| `Zlt_le_succ` (②) | top50 엔 CoRN 이름만. 풀 9,957개에 실제로 있음 @Coq표준 ZArith ✓ |
| `gupaco5_mon` (②) | top50 은 `gpaco5_*`. 풀 1,312개에 있음 @같은 프로젝트 ✓ |
| `CompIdLeft` (④) | 풀 683개에 없고 **db 직접조회도 0건** ✓ |
| `ratAdd_eqRat_compat` | 풀 8,389개엔 없지만 db 엔 2건 @adampetcher-fcf → ③a 와 일치 ✓ |

### 한계

- **첫 lemma 기준 표는 낙관적**이다. 전부 기준으로는 40.6% → 35.8%.
- 이름은 **마지막 성분**으로 비교한다 (`Pos.lt_succ_r` → `lt_succ_r`). 동명이인 오탐 가능.
- lemma 추출기가 완벽하지 않다 (자체 테스트 12건 중 11건 통과).
- 표본 노이즈: 589~670건 기준 ±3.6~4.2pp.
- CompCert 프로브 파일(`goldsft_bs2.jsonl`)은 **후보 50개로 고정 저장**돼 있어 학습 설정
  (`num_premises: 100`)과 다르다. CompCert 수치는 그만큼 비관적이다.

### 측정 중 겪은 함정

- **BM25 유사증명 검색이 예제당 수십 초**를 먹는다 (py-spy 로 확인: 병목이 premise TF-IDF 가
  아니라 `proof_retriever` 의 bm25 였다). `proof_ret` 를 conf 에서 빼면 건너뛴다 —
  55분 걸리던 측정이 **90초**로 줄었다.
- `proj_of` 경로 파싱: `/coq-dataset/repos/<owner>-<repo>/` 에서 "coq-dataset" 을 먼저
  매칭하면 프로젝트가 전부 `"repos"` 로 뭉개져 **항상 같은 프로젝트**가 된다. 이 버그로
  수집 로직 비율이 12.4% 로 부풀었다 (수정 후 3.6%, 5000건에서 2.9%).
- 지역 가설(`Hi`, `H_bt22'_node`, `eq1`)이 lemma 로 잡히면 "데이터셋 밖" 이 부풀어 오른다.

## 9. 다음 단계

**아직 아무것도 해결되지 않았다.** 원인 규명과 해법 실증까지만 왔고, 실제 데이터는 그대로다.

- 적용가능성 재랭킹은 **순서만** 바꾼다 → 이 문제엔 +0.8pp
- `search_query.py` 는 질의 문자열을 만들 뿐 **아직 아무 곳에도 안 붙었다**

### 남은 작업

1. **Coq 질의 실행기** — 질의를 날리고 diagnostics 에서 이름+statement 를 파싱해 `Sentence`
   로 만드는 코드
2. **후보 병합** — 결과를 `example.premises` 에 합치기
3. **배선 지점 결정** ← 설계 판단 필요
   - 데이터 생성 시점: 학습·추론이 같은 분포를 보지만 전체 재생성 필요 (예제당 ~70ms)
   - 추론 시점만: 싸지만 학습 때 못 본 정보가 들어옴
4. **재측정** — 35.8% 가 얼마나 오르는지

### 질의 생성기 보완 (5.2 에서 드러난 것)

| 항목 | 겨냥 |
|---|---|
| 커스텀 `Notation` 을 연산자 표에 반영 | A 17.9% 의 상당 부분 |
| 가설 방향 질의 (`apply X in H`) | D 13.7% |
| 등식 질의를 양방향으로 | B 2.0% 의 절반 |
| 질의 크기 상한 | 지나치게 구체적인 질의로 0건 나는 것 |
| 반환 상한 K=10 | 한 질의가 정원 21개를 다 먹는 것 |

### 먼저 해볼 값싼 실험

**retrieval 쿼리를 현재 goal 결론으로 좁히면 recall 이 오르나** (5.3). 데이터 재생성도
Coq 실행도 필요 없고 쿼리 문자열만 바꾸면 된다. ②(38.4%) 가 여기서 상당 부분 설명되면
SearchPattern 통합보다 훨씬 싸게 이긴다.

### 우선순위 판단

- **SearchPattern 통합** — 51.1% 를 데이터 재생성 없이 겨냥. 최우선.
- 수집 로직 수정 — 2.9% 뿐. 재생성 비용 대비 우선순위 낮음.
- dense retriever 학습 — 장기 과제.
