# v9 프롬프트 vs 기존 rango 프롬프트

같은 스텝(40개)에서 두 파이프라인이 만드는 프롬프트를 그대로 나란히 뽑았다.

## 무엇이 다른가

| 설정 | rango 원본 | v9 |
|---|---|---|
| premise_tokens | 512 | 896 |
| proof_tokens | 1024 | 256 |
| hard_seq_len | 4096 | 2048 |
| num_premises | 50 | 100 |
| num_proofs | 20 | 12 |
| 검색 | tfidf 만 | tfidf + 구조 재랭킹 |
| [TYPES]/[DEFINITIONS] | 없음 | 주입 |
| 이름 정규화 | 없음 | 전부(rate 1.0) |
| cut | 없음 | gold 가 없으면 assert 치환 |

토크나이저는 **둘 다 Qwen** 으로 맞췄다 — 예산 차이만 남기고 나머지 변수를 없애야 비교가 의미 있다.

## 자동 점검 요약

- **1건** ★★ 2048 절단으로 [PREMISES] 헤더 소실 (전체 2638토큰)

## 내가 훑어본 결과 (40건 전수)

### 버그는 없었다

자동 점검에 걸린 4종을 전부 파보니 **전부 오탐**이었다.

| 걸린 것 | 실제 |
|---|---|
| 같은 `L#` 가 두 번 선언됨 (9건) | `[PREMISES]` 의 **문장**과 `[PROOFS]` 의 **증명**이 같은 lemma 를 보여주는 것. `[PREMISES]` 안에서의 중복은 **0건** — 매핑은 단사다. rango 도 같은 중복이 12건 있다 |
| `[PROOFS]` 가 비어 있음 (5건) | 증명 시작 지점이라 유사 증명이 없다. rango 도 똑같이 비어 있다 (ex_003 은 양쪽 다 47토큰) |
| 정규화 이름이 하나도 없음 (2건) | 그 스텝에 주입할 프로젝트 정의가 없다. 문서에 적힌 "94% 가 ≥1개 치환 가능" 과 맞는다 (2/40 = 5%) |
| v9 가 rango 의 절반 미만 (2건) | 아래 ★ 참고 — `proof_tokens` 축소 때문이다 |

`ex_010` 이 의도가 그대로 작동하는 사례다.

    rango 정답:  now apply ok_middle_comm.     ← 이름 암기로 낼 수 있다
    v9   정답:  now apply L0.                 ← [PREMISES] 를 읽어야만 낼 수 있다

`L0 : forall {A} (E : context A) F G H, f0 (E++F++G++H) -> f0 (E++G++F++H)` 가
프롬프트에 있고 goal 이 `f0 (E ++ G ++ F ++ H)` 이므로, **문장을 읽어 goal 과 맞추는**
것 외에 방법이 없다.

### ★ 그런데 설계 쪽에서 큰 것이 나왔다 — `[PROOFS]` 가 4.3배 줄었다

40건 합계:

| 섹션 | rango 중앙 | v9 중앙 | 합계 변화 |
|---|---|---|---|
| PREMISES | 498 | 775 | 12,649 → 20,125  (**+59%**) |
| **PROOFS** | **952** | **221** | **26,792 → 7,217  (−73%)** |
| STATE | 100 | 100 | 6,459 → 6,477 |
| SCRIPT | 71 | 67 | 6,187 → 6,067 |
| TYPES | — | — | 0 → 719 (신규) |
| DEFINITIONS | — | — | 0 → 1,170 (신규) |
| **전체** | **1,633** | **1,326** | **−19%** |

`[TYPES]`/`[DEFINITIONS]` 로 **1,889 토큰을 더했는데 `[PROOFS]` 에서 19,575 토큰을 뺐다.**
순증이 아니라 **순감**이다 — 모델이 보는 정보가 rango 보다 19% 적다.

원인은 둘이다.

  · `proof_tokens` 1024 → 256   (v8 에서 640, v9 에서 256 으로 두 번 줄였다)
  · `hard_seq_len` 4096 → 2048  (전체 문맥이 절반)

**`proof_tokens` 축소는 속도에 거의 기여하지 않는다.** 비용은 bm25 **검색**에 있고
(`num_proofs` 20 → 12 가 그 부분이다), `proof_tokens` 는 이미 검색해 온 것을 **자를 뿐**이다.
속도 개선의 실체는 `metadata_only`(132배)·메모이제이션·캐시 크기·fork-safe SQLite 였다.
즉 **얻은 것 없이 가장 중요한 문맥을 줄였을 가능성이 크다.**

### 되돌릴 때의 제약

`hard_seq_len 2048` 안에서 섹션 예산 합은 이미 초과 상태다
(896+256+512+1024+300+300+128 = 3,416). `proof_tokens` 를 올리면 초과가 커지고
앞쪽(=하위 premise)이 더 잘린다. 다만 절단 감사 405건에서 **정답이 쓰는 이름이 잘려
사라진 경우는 0건**이었다 — 좋은 premise 는 뒤쪽에 놓이고 절단은 앞부터 먹기 때문이다.

선택지는 둘이고, 어느 쪽도 공짜가 아니다.

  ⓐ `hard_seq_len` 을 3072~4096 으로 올린다 — 학습 속도·메모리 비용
  ⓑ `proof_tokens` 만 올린다 (예: 256 → 640) — 하위 premise 가 더 잘린다
